# Native food compatibility hardening — issue #444

This is the fourth source-only coding slice, stacked on #618 -> #614 -> #608.
It addresses five concrete pretest blockers without changing Packwiz, selected
native JARs, recipes, user worlds or assembled integration branches.

## Canonical Gilded classification

Every active Gilded `food_restriction` now accepts exactly one or more of:
`#c:foods/nether_only`, `#c:foods/golden`,
`#tmm:foods/magical`, or (only if the effect has `lava_caught=true`)
the **actual** `minecraft:custom_data` stack marker
`tyr_progression:lava_caught=true`. Earned beverages and the configured
baseline-alcohol exception remain separate limited allowances.

`GildedMechanics.foodBonusMatches` uses only the canonical Golden tag when
`gold_recipes=true` is configured. It no longer invents Golden nutrition for
an item merely containing a nugget in some recipe. Raw/cooked nether-only
food does not get the Golden bonus; neither does merely being magical.
Other Paths' independent `food_restriction` effects retain their own
selectors and do not automatically inherit Gilded eligibility.

Additive, `replace:false` common tag seeds include three vanilla Golden
foods, two source-verified optional My Nether's Delight Golden Eggs, and the
four owner-reviewed vanilla Nether-obtainable foods (porkchops, cooked
porkchops, rotten flesh, mushroom stew). These are **bootstrap classification
seeds**, not a claim of complete generated Nether provenance. Their
extensions remain generated by the recipe/loot classifier and third-party
datapacks, with the owner's exact nether_only proof requirement. The class
`#c:foods/with_nether` is **not** equivalent to Gilded eligibility.

## Universal Magical and custom-use items

`#tmm:foods/magical` explicitly lists the seven approved starting items,
including the Enchanted Golden Apple and approved optional Spectrum, EvilCraft
and Botania IDs. Plain Golden Apple/Golden Carrot are **not** classified
magical. Optional mod IDs are marked `required:false` to avoid failing
loading when the provider is absent. No names, enchantment or status effects
infer magical status.

Only the audited custom-use food-like items
`evilcraft:flesh_rejuvenated` and `botania:infinite_fruit` appear in
`#tmm:foods/custom_use`. Strict Paths can deny other tagged custom-use
consumables, and magical ones pass dietary checks, without assigning any
FoodProperties. The upstream mod still handles charges, native resources,
original use and return effects; the shared food engine never adds hunger,
mana or blood to non-FOOD custom-use stacks. The existing DS legacy
special-use overrides (0/0) are not replaced by speculative values.

## Recreational drinks with no free nourishment

An earned `diet_permission` or approved Gilded baseline alcohol exception
authorizes consumption and original non-food effects. It is **not** a food
source by itself. For a component-backed otherwise off-diet drink, Dragon
Survival's existing item food-property hook receives a new 0/0 nutritional
projection with original conversion, effects and use duration; the server
also remembers the very last completed-use food values and removes **only
positive** hunger/saturation gains at Finish for JAWR/Gilded whose native
handlers may add them after vanilla dispatch. Completed consumption,
ownership and exact ItemStack components must match; canceled or interrupted
use cannot be credited. Never alter JAWR blood or native potion effects.

If the recipe/profile already establishes separate legitimate nourishment,
or the item is universally magical, the permission does not erase it.
Unknown, no-FOOD potion-style items are left entirely to native use. A dedicated S2C `B` permission-only entry keeps the DRINK action enabled
even at full hunger, with 0/0 food and untouched effects/container. The
drink category is guarded by actual `UseAnim.DRINK`, granted permission
and active physiological form; merely holding a drink or a broad tag
does not award nutrition.

## Stack-aware client decisions

The diet S2C entry schema adds `L` (lava-caught marker grants original
native food behavior, else deny) and `LN\\t<count>\\t<sat>` (marker
grants exact validated Dragon nutrition, else deny). The server computes
both marked and unmarked variants via the **same** Gilded check on an
actual copied stack; it only emits conditional entries when a real marker
changes the decision. An independent strict veto always stays a DENY.
The local DS food-property bridge checks the stack's real
`minecraft:custom_data` value instead of whitelisting every cooked cod
because one copy was lava-fished. Transfer format remains bounded,
transactional, and server-authored.

## JAWR cuisine #450 reconciliation

`BloodCuisineVampireFoodMixin` in independent PR #607 intercepts the
**private instance** `VampireEvents.isSolidFood(ItemStack)` at method HEAD
for a source-audited, receipt-charged Blood Cuisine item only.
This stack's `JawrVampireFoodPenaltyMixin` intercepts the result at the
callsite in `onItemUseFinish`, allowing only earned recreational drinks,
explicit safe-food tags or universal magical items to bypass the native
food-sickness predicate. If a #607 receipt is correctly charged, its HEAD
interceptor returns false, and the later callsite modifier retains false;
if uncharged, no general item-ID safe-food tag clears the penalty.
Neither bridge invokes `BloodPoolHandler` or pays blood. The exact pin
remains JAWR 0.5.39.

The safe-food tag starts **intentionally empty**: neither blood sausage nor
pie may be whitelisted by ID, because doing so would bless forged/uncharged
versions. The existing #607 anti-duplication receipt ledger and 1,000-blood
credit are not copied into this branch. Resolve the separate pinned BnC
sausage/cask dependency before promising the full #450 cuisine.

## Tests and handoff

Source tests validate the explicit seven magical IDs, optional sources,
independent Golden/Nether tags, absence of unverified broad cuisine-safe
tags, pure permission-only policy and strict priority, and the new client
lava-caught packet modes. Pinned Java Gradle compile/CI does **not** validate
JAWR bytecode mixin application, native completed-use event ordering, modded
food-specific `getFoodProperties` behavior or native custom-use activation.
Those remain deliberate owner-authorized type B/C QA acceptance checks.

The route census and generated food-source coverage remain separate, as do
Monk food discovery (#609), Elixir of Life (#610) and the genuine BnC-native
Blood Wine/Sausage hold (#450). Integrate all dependency branches in order
before launching a focused food gameplay test.
