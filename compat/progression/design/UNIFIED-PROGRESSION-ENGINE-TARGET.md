# Unified Progression — owner-approved architecture and implementation survey

**Decision date: 2026-11-18. Status: LOCKED DESIGN TARGET; implementation not authorized by this document.** Supersedes older statements that MXP and Tyz must remain separate external modules and the historical nine-tree design where they conflict. Preserve reference research and working runtime until a separately reviewed migration.

## Architecture and licensing
- Retain `tyr_progression` as the one independently installable, data-driven player enhancement engine. Absorb the existing `tmm_mxp` module and selectively adapt Tyz's Skills source; eventually remove both external runtime JAR requirements. Do not introduce a fourth skill framework. Transformations remains a separate optional provider; JAWR, Goety and Dragon Survival own their physiology and native state.
- All first-party mods are to be released under MIT. Add appropriate first-party copyright/license files and mod metadata, preserve full upstream notices in sources and distributed JARs, maintain THIRD_PARTY_NOTICES.md with immutable provenance; do not relicense third-party assets/dependencies. Confirm rights/holder before publication. Tyz upstream LICENSE states MIT (Copyright 2026 Tyzbrand), public 6.4.2 release says MIT; source gradle.properties says All Rights Reserved, an inconsistent metadata field requiring clarification/provenance check before importing substantial code. JDT 1.21.1 LICENSE.txt is MIT (Copyright 2023 Direwolf20-MC). Create 1.21.1 LICENSE.md is MIT for code (Copyright The Create Team / The Creators of Create), but explicitly reserves all rights to src/main/resources/assets; do not import those assets.
- One authoritative built-in MXP/SP wallet plus an extensible registry of independently configured named experience systems, each with its own wallet; all effects are owned by the player through innate grants or skill tree unlocks. Trees may default to a currency and individual skills may override it. No duplicate XP sinks or automatically converted currencies. Preserve existing MXP formula, nominal cost/actual successful debit, configurable growth default 1.02, 1000 effective MXP per SP, first boss/ritual awards, transaction dedupe and lifetime level divisor. Existing native Monk/Hunter progression and provider milestones stay meaningful; configuration decides which ownership/currency a skill uses.
- Ten TMM trees: Core Skills (universal), Monk, Hunter, Gilded, Vampire, Werewolf, Lich (either Goety or JAWR Forbidden Magic; Archlich accesses one tree once), Cave Dragon, Forest Dragon, Sea Dragon. Combined forms use eligible constituent trees subject to compatibility policy; no bespoke hybrid tree at present. No forced assignment of new abilities or balance values in this change.
- Every skill, discipline, innate grant and effect definition is declarative; reusable engine-owned Java handlers and optional API extensions implement mechanics once. No path-owned runtime logic. Standalone engine must not require any of the reference mods.

## Reference expressiveness
**Player-only ownership (owner decision, 2026-11-18):** Progression supports innate/automatic/form-granted abilities and player-owned skill tree unlocks/ranks only. Research, item/resource costs, rituals, timed prerequisites and permanent installation-themed unlocks are flavors of acquisition for the same player-owned nodes, not an independent augment inventory or ownership type. A learned ability may be toggled inactive without changing ownership; configured skill-tree respec remains distinct from detachable traits. No equipment-owned effects, item affixes, gem/perk sockets, transferable/collectible ability tokens, uninstall/extraction/refund systems for removable installed traits, or ability trading/PvP theft. Equipment/item conditions for player-owned effects remain allowed; do not alter other mods' native equipment systems. Reference mods are donors of useful player-effect algorithms and acquisition/graph mechanics only, not full ownership parity. This supersedes earlier broad parity targets.

See [scoped reference expressiveness](REFERENCE-CAPABILITY-PARITY-TARGET.md). Retain useful player-effect algorithms, Oritech research/acquisition, Everlasting ranked persistent effects, Astral branching/attunement mechanics, and Apotheosis proc/attribute mechanics. Equipment and transferable ownership are out of scope.

### Vision development target
Two separately selectable handler capabilities, e.g. `enhanced_night_vision` and `lava_vision` (names provisional). JDT's [1.21.1 LightTextureMixin](https://github.com/Direwolf20-MC/JustDireThings/blob/1.21.1/src/main/java/com/direwolf20/justdirethings/mixin/LightTextureMixin.java) wraps lightmap night-vision checks and intensity; adapt eligibility to Progression-synced state instead of the helmet's ability and durability. Do not require JDT. Preserve ordinary vanilla Night Vision/Blindness/Darkness semantics when enhancement disabled; explicitly define precedence when active, test shader compatibility (JDT has reported shader issues). Lava vision should reduce/remove submerged lava fog/obscuring overlay to make legitimate underwater-in-lava navigation practical; no block x-ray, no fire immunity, no modification of fluid physics, no out-of-lava global fog changes. Source-verified alternative: [Create 1.21.1 ClientEvents.getFogDensity](https://github.com/Creators-of-Create/Create/blob/mc1.21.1/dev/src/main/java/com/simibubi/create/foundation/events/ClientEvents.java) uses NeoForge ViewportEvent.RenderFog, checks camera position below fluid surface, skips spectators, and when wearing a netherite diving helmet in lava sets near plane -4 and far plane 20 blocks then cancels the event. Adapt only the fog calculation, not helmet, backtank, water-visibility or damage-immunity mechanics. 20 blocks is a reference default proposal, not a locked balance value; configurable far distance. This avoids a lava-fog mixin. Pin exact donor commit and include original MIT notice if reusing; no Create dependency, no assets. Rendering overlay, shaders and exact in-game behavior remain untested. Test entry/exit, both toggles, cure/respec/death, multiplayer, dedicated server classloading, water and shader modes. Do not assign these to particular trees yet.

## Owner update — named experience systems and pre-stable saves (2026-11-18)

**Final approved XP architecture (supersedes all three-channel/one-tree-one-currency proposals):** Progression owns an extensible registry of namespaced experience systems and persistent per-player XP/point wallets, with no arbitrary three-system limit. MXP is a built-in system with its existing magic-debit, first-completion and growth policy. Other experience systems are independently defined in datapack JSON, not owned by any tree or discipline. A pack may define one, several or no additional systems. Normal technical validation and resource bounds are appropriate; no fixed gameplay slot count.

### Data contract and boundaries

- Proposed resource location: `data/<namespace>/tyr_progression/experience_systems/<name>.json`. A definition owns its ID, display metadata (name, point name, icon/color), curve or explicit thresholds, points per level, starting grants, sources, source conditions, optional award multipliers and acquisition/earning rules. A source is a trusted event/adapter plus data parameters; do not add executable path scripts. Preserve current native Monk/Hunter curves and awards when extracting them. MXP's built-in identity is reserved, server-tunable under existing rules; no shadow duplicate MXP economy.
- Tree definitions remain separate. A tree may declare a default currency; an individual skill can override it. Different skills in one tree may use different currencies, and multiple trees may spend the same currency. A skill declares its cost and any currency-specific level requirement explicitly (or inherits the tree default). Initially one currency per purchase; no implicit exchange, pooled balances, or multi-currency payment requirement. Automatic ranks/grants and prerequisites may reference a named system's level independently of purchase currency. Tree enrollment and ownership are independent of wallet enrollment/earning.
- Each currency is credited once per matching configured source/committed action, not once per eligible tree. Intentional multiple source matches or multiple independent currencies require an explicit policy; no multiplication through tree membership. A source may require a path/form flag. Levels and balances belong to wallets; acquired ranks, milestones and effects belong to tree/skill owners. Server transactions validate eligibility, prerequisites, cost, and balance atomically, and refunds return only to the currency charged. Stable ownership and paid-cost receipts prevent repeated grants/refund exploits. One authoritative award path for built-in MXP.
- Monk cultivation, Hunter advancement and possible Gilded advancement are ordinary data-defined examples, not special slots and not a mandate to create a Gilded economy. Ten pack trees remain the content target, not an engine limit. No new roster, costs, or curve changes approved in this update.
- All acquisition, abilities, hooks, effects, conditions, bonuses and attributes are reusable engine-owned implementations with configurable parameters. No discipline-owned Java or gameplay scripts. Existing Transformation probes supply authoritative form observations; unknown is not permission. Epiphany remains primary UI/architecture donor and Tyz imports stay paused until clarification.
