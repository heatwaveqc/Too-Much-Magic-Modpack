# Too Much Magic — repository-wide agent safety and CI rules

This file applies to all AI agents, automated contributors, coding workflows, scheduled tasks, and branches in this repository. For detailed integration procedures read [the active integration branch contract](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/AGENTS.md) and [build channels](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BUILD-CHANNELS-AND-TESTING.md).

## Progression ownership and branch coordination (owner policy, 2026-11-16)

- **All executable progression functionality belongs to the single `compat/progression` / `tmm_progression` engine**, including Java, API/schema, effect handlers, event hooks, mixins, networking, commands, adapters, runtime scripts and executable tests. Prefer reusable data-driven capabilities. Monk, Hunter, Gilded and all future paths are **config-only**: path/datapack JSON, Tyz skill-tree/config JSON, tags/data assets, localization, non-executable fixtures and documentation. Class/path branches do not own or add Java/KubeJS/other runtime code; if a path needs new behavior, implement it in a separate engine PR.
- **Branch hierarchy:** `main` is the accepted bootstrap/policy base; `test/full-integration` is the unified modpack integration and authorized QA source; `dev/progression` is the long-lived coherent Progression subsystem integration branch. `feature/progression-*` contains engine changes and `feature/monk-*`, `feature/hunter-*`, `feature/gilded-*` (etc.) contain only path configuration. Start these feature branches from `dev/progression`, merge back into it by PR and designated Progression writer, then promote reviewed coherent subsystem slices into `test/full-integration` by the modpack integration writer.
- **Before starting/resuming work**, search related Issues/PRs/branches and current integrated code; never duplicate a completed implementation. Use isolated agent branches, one writer per shared branch, recoverable pushed commits, explicit edited paths/dependencies/tests/next steps in the PR handoff. Synchronize active class branches with shared Progression, and reconcile relevant changes from full integration back into Progression via reviewed PRs. No direct writes, shared-branch force pushes, stale directory restores or untracked branch deletions. Existing noncompliant legacy branches require inventory/migration; do not assume they already follow this structure.
- Read the [complete branch and configuration-ownership workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BRANCH-AND-PROGRESSION-WORKFLOW.md). This policy changes how work is authored and merged, **not** the owner authorization requirements for Integration Assembly, Server Boot Smoke or Prism QA Package.

## Integration source lifecycle and required quick merge checks (2026-11-16)

- **One integration writer:** feature agents work on PR branches and hand off exact source paths, dependencies, and acceptance tests. Shared `test/full-integration` manifests, quest/config ownership and packwiz hashes must be reconciled by the integration writer against the latest HEAD; never blindly replay older directories.
- **Freeze all external donors to full immutable commit SHAs.** When source is merged into integration, convert its stream to baseline-owned and record original branch, PR and merge commit *before* GitHub auto-deletes the temporary feature branch. Merged does not mean a moving feature branch remains a valid dependency.
- **Never use `[skip ci]` on integration-impacting work.** Repository CI, Module CI, and Integration Preflight are always allowed and should be required at merge; they must remain separate from full NeoForge boot or Prism package generation. Resolve checkout dirtiness, line endings, stale source references and path collisions before merging.
- **No automatic source assembly either.** On push/PR run read-only source preflight and scoped compilation/unit tests. Run `Integration Assembly` only with explicit owner authorization (`assemble_only=true` or `full_smoke=true`). A new draft feature branch is only an advisory in routine preflight; every feature reported ready for live testing still requires an inclusion attempt in the next comprehensive QA.
- Use the [canonical eight QA levels](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/qa/TEST-LEVELS-AND-TERMINOLOGY.md): **Repository CI, Module CI, Integration Preflight, Integration Assembly, Server Boot Smoke, Prism QA Package, Client Launch Smoke, Gameplay Acceptance**. Quick CI is only the first three. Never conflate a generated Prism ZIP with a launched or gameplay-tested client.
- Repository branch protection must require lightweight `Verify bootstrap / metadata` on integration PRs without requiring a full smoke. See [admin checklist](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/qa/BRANCH-PROTECTION-SETUP.md). Text and CODEOWNERS alone do not create branch protection.

## No automatic Minecraft builds or QA packages (2026-11-16)

- **Never configure `push`, `pull_request`, `schedule`, or an unguarded reusable workflow to start a full NeoForge server, package a Prism test ZIP, download the whole mod roster to build a release, tag a tested snapshot, or publish build artifacts.** These activities require a separate explicit owner-approved manual invocation for that run.
- Static validation, configuration/manifest checks, targeted compilation and isolated unit tests may continue automatically as **quick CI**, provided they do not boot the complete modded game or produce a release/Prism build.
- Any new build-capable workflow must expose a default-false explicit approval input (`assemble_only` for source assembly, `full_smoke` for Minecraft server tests, `authorized_build` for packaging-only work), and its build job must check manual `workflow_dispatch` (or a reusable call traceable to an owner-authorized manual launcher) **and** that opt-in. Be especially careful with `||`/OR conditions: wrap branch-name alternatives in parentheses so the authorization gate applies to every branch.
- Existing legacy workflows were migrated to manual opt-in on their owning feature/build branches. **Do not copy or restore their old automatic triggers** when rebasing/cherry-picking.

## Owner approval required before any full Minecraft server smoke

- **By default, do not run a full modded NeoForge server smoke test.** Routine development checks are source/manifest/packwiz/quest/config validation, syntax checks, Java compilation and unit tests. Label these `QUICK CHECKS` or `STATIC/COMPILE PASS`, not `server-smoked`.
- **A new, explicit owner instruction is required for each full server smoke run.** Completing a feature, opening/merging a PR, updating the test branch, preparing a test build or test plan, checking build readiness, or ordinary permission to run tests is **not** approval to start a modded dedicated server.
- Agents must not manually dispatch, schedule, retry, use `workflow_call`, run `scripts/smoke_server.sh`, or indirectly trigger a full smoke via push to a legacy branch without such approval. Do not bypass this rule through alternate workflows, renamed scripts, or CI edits. Disable unguarded automatic full-smoke triggers before pushing to a branch that has them.
- The active [full integration workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/.github/workflows/full-integration.yml) defaults to fast validation/compilation. Its opt-in `full_smoke: true` input is permitted **only** following an explicit instruction from the owner for that run. Only then may CI boot the full NeoForge mod roster, freeze a server-tested integration snapshot and publish the corresponding tested Prism QA ZIP.
- Do not mark quick checks as in-game/server compatibility success, publish a smoke-tested build without the test, or promote a candidate/stable build without the established verification gates.
- Preserve the 2026-11-15 overnight test already in progress; **do not cancel or restart it**. This rule governs subsequent invocations.

When in doubt, complete the quick checks and report that the full smoke remains **NOT RUN — OWNER APPROVAL REQUIRED**. This instruction supersedes any older text in historical workflows or documentation suggesting an automatic full boot after each change.
