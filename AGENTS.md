# Too Much Magic — repository-wide agent safety and CI rules

This file applies to all AI agents, automated contributors, coding workflows, scheduled tasks, and branches in this repository. For detailed integration procedures read [the active integration branch contract](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/AGENTS.md) and [build channels](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BUILD-CHANNELS-AND-TESTING.md).

## Task selection: live design chats vs scheduled Work (owner guideline, 2026-11-20)

- **Live, owner-attended chats are design-first by default.** When choosing an open item to tackle next in a live conversation, favor work that benefits from owner decisions: mechanics, progression, balance, mod inclusion, architecture, ambiguous requirements, and tradeoffs. Investigate options and obtain the owner's decision rather than silently inventing one.
- **The hourly scheduled Work chat is execution-first by default.** Its first choice is already approved, well-specified work that needs no new owner design decision. Prefer current-sprint tasks, observe the scheduled task's eligibility/inactivity criteria, and verify existing Issues, PRs, branches, and assigned work before taking ownership to avoid duplicate implementations.
- **This is a selection preference, not a prohibition.** If the owner explicitly requests coding, integration, fixes, testing, documentation, or other implementation in a live chat, do that work there under the normal branch/CI/QA and ownership rules. A live chat may also complete a straightforward task when appropriate; do not bounce an explicit request to automation.
- **Escalate unresolved choices; do not guess.** Scheduled agents should document the design question and hand it to a live discussion, then select another unblocked execution task. Neither lane may override approved scope, designated writers, or the separate authorization gates for full builds and QA.

## Progression ownership and branch coordination (owner policy, 2026-11-16)

- **All executable progression functionality belongs to the single `compat/progression` / `tmm_progression` engine**, including Java, API/schema, effect handlers, event hooks, mixins, networking, commands, adapters, runtime scripts and executable tests. Prefer reusable data-driven capabilities. Monk, Hunter, Gilded and all future paths are **config-only**: path/datapack JSON, Tyz skill-tree/config JSON, tags/data assets, localization, non-executable fixtures and documentation. Class/path branches do not own or add Java/KubeJS/other runtime code; if a path needs new behavior, implement it in a separate engine PR.
- **Branch hierarchy:** `main` is the accepted bootstrap/policy base; `test/full-integration` is the unified modpack integration and authorized QA source; `dev/progression` is the long-lived coherent Progression subsystem integration branch. `feature/progression-*` contains engine changes and `feature/monk-*`, `feature/hunter-*`, `feature/gilded-*` (etc.) contain only path configuration. Start these feature branches from `dev/progression`, merge back into it by PR and designated Progression writer, then promote reviewed coherent subsystem slices into `test/full-integration` by the modpack integration writer.
- **Before starting/resuming work**, search related Issues/PRs/branches and current integrated code; never duplicate a completed implementation. Use isolated agent branches, one writer per shared branch, recoverable pushed commits, explicit edited paths/dependencies/tests/next steps in the PR handoff. Synchronize active class branches with shared Progression, and reconcile relevant changes from full integration back into Progression via reviewed PRs. No direct writes, shared-branch force pushes, stale directory restores or untracked branch deletions. Existing noncompliant legacy branches require inventory/migration; do not assume they already follow this structure.
- Read the [complete branch and configuration-ownership workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BRANCH-AND-PROGRESSION-WORKFLOW.md). This policy changes how work is authored and merged, **not** the owner authorization requirements for Integration Assembly, Server Boot Smoke or Prism QA Package.

## Preferred obsolete-branch cleanup: audited GitHub Actions retirement (owner decision, 2026-11-16)

**Use GitHub-side, SHA-guarded branch retirement as the default for obsolete remote branches.** The proven implementation is [the audited cleanup workflow](.github/workflows/retire-orphan-branches-2026-11-16.yml), [retirement script](scripts/retire_orphan_branches.py), and [frozen first-batch manifest](scripts/retired-branches-2026-11-16.json), introduced by [PR #266](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/pull/266). That run removed 46 approved remote branches without restoring their code or requiring a local Git client. GitHub's automatic source-branch deletion after a *normal meaningful PR merge* is also fine. **Do not refresh obsolete branches, create dummy PRs, force-rebase/reset them, or merge their old contents simply to make deletion possible.**

**For each new cleanup batch:**

1. Re-inventory the current refs and review each candidate against `test/full-integration`, `dev/progression`, merged/superseding PRs, the source/provenance locks (especially `manifest/integration-sources.json`), open PR **heads and bases**, QA/readiness handoffs, and other outstanding dependencies. Preserve needed work and immutable provenance first; do not equate a closed PR or a file that exists on baseline with fully integrated behavior. Explicitly exclude protected, active, uncertain, or unreconciled branches.
2. On an isolated maintenance branch from current `main`, prepare an **independently reviewed, batch-specific allowlist** of exact branch names and full 40-hex head SHAs; modify or generalize the runner/workflow safely for that batch. **The existing 2026-11-16 manifest and runner are intentionally one-shot (the runner enforces exactly 46 entries); they are not a reusable list for new branches.** Do not expand the old frozen list silently or infer approval from an old cleanup.
3. Open a maintenance PR to `main`. Require a read-only PR dry run with the current refs and manifest, review its full READY/SKIP/ERROR report, confirm the intended list and that no branch changed, and review GitHub Actions permissions/triggers. Keep the deletion step separate from modpack source merges and all full server/Prism builds.
4. Execute deletion **only for that specifically reviewed batch**, through the `main` GitHub Actions workflow after approval/merge or an explicit authorized manual dispatch. The job must recheck the exact ref SHA immediately before deletion and **fail closed/skip** protected names, open-PR heads/bases, active frozen source streams, missing/changed refs, or uncertain conditions. A push-triggered one-shot workflow must be scoped to the reviewed maintenance PR; never enable broad or scheduled unattended pruning.
5. Verify the finished Actions run and per-branch deletion/skip/error counts, re-list remote branches, confirm all held branches remain, and record the PR/run/commit as provenance. For a local clone, `git fetch --prune origin` only clears stale remote-tracking refs; it does not delete local working branches.

**Capability boundary:** GitHub connector operations may support commits and PR merges but not arbitrary remote ref deletion. Agents should use the reviewed Actions retirement mechanism when deletion is needed, rather than claiming the operation cannot be automated or taking destructive shortcuts. All existing single-writer, protected-branch, integration-source, and explicit full-build authorization rules remain in force.

## Integration source lifecycle and required quick merge checks (2026-11-16)

- **One integration writer:** feature agents work on PR branches and hand off exact source paths, dependencies, and acceptance tests. Shared `test/full-integration` manifests, quest/config ownership and packwiz hashes must be reconciled by the integration writer against the latest HEAD; never blindly replay older directories.
- **Freeze all external donors to full immutable commit SHAs.** When source is merged into integration, convert its stream to baseline-owned and record original branch, PR and merge commit *before* GitHub auto-deletes the temporary feature branch. Merged does not mean a moving feature branch remains a valid dependency.
- **Never use `[skip ci]` on integration-impacting work.** Repository CI, Module CI, and Integration Preflight are always allowed and should be required at merge; they must remain separate from full NeoForge boot or Prism package generation. Resolve checkout dirtiness, line endings, stale source references and path collisions before merging.
- **No automatic source assembly either.** On push/PR run read-only source preflight and scoped compilation/unit tests. Run `Integration Assembly` only with explicit owner authorization (`assemble_only=true` or `full_smoke=true`). A new draft feature branch is only an advisory in routine preflight; every feature reported ready for live testing still requires an inclusion attempt in the next comprehensive QA.
- Use the [canonical eight QA levels](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/qa/TEST-LEVELS-AND-TERMINOLOGY.md): **Repository CI, Module CI, Integration Preflight, Integration Assembly, Server Boot Smoke, Prism QA Package, Client Launch Smoke, Gameplay Acceptance**. Quick CI is only the first three. Never conflate a generated Prism ZIP with a launched or gameplay-tested client.
- Repository branch protection must require lightweight `Verify bootstrap / metadata` on integration PRs without requiring a full smoke. See [admin checklist](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/qa/BRANCH-PROTECTION-SETUP.md). Text and CODEOWNERS alone do not create branch protection.

## No automatic Minecraft builds or QA packages (2026-11-16)

- **Never configure `push`, `pull_request`, `schedule`, or an unguarded reusable workflow to start a full NeoForge server, package a Prism test ZIP, download the whole mod roster to build a release, tag a tested snapshot, or publish build artifacts.** These activities require a separate explicit owner-approved manual invocation for that run.
- Static validation, configuration/manifest checks, targeted compilation and isolated unit tests may continue automatically as **quick CI**, provided they do not boot the complete modded game or produce a release/Prism build.
- Any new build-capable workflow must expose a default-false explicit approval input (`assemble_only` for source assembly, `full_smoke` for Minecraft server tests, `authorized_build` for packaging-only work), and its build job must check manual `workflow_dispatch` (or a reusable call traceable to an owner-authorized manual launcher) **and** that opt-in. Be especially careful with `||`/OR conditions: wrap branch-name alternatives in parentheses so the authorization gate applies to every branch.
- Existing legacy workflows were migrated to manual opt-in on their owning feature/build branches. **Do not copy or restore their old automatic triggers** when rebasing/cherry-picking.

## Mandatory mod update review before every full build (owner decision, 2026-11-17)

- **Every explicit full-build request must begin with a read-only update survey of the entire active mod roster**, before freezing the candidate SHA or dispatching Assembly + Server Boot Smoke / Prism QA Package or a full release build. Read the active packwiz index and pins, not just the desired manifest. Include dependencies and all supported upstream platforms (Modrinth, CurseForge, GitHub/custom sources); distinguish first-party source rebuilds from external releases.
- Compare pinned versions with compatible upstream releases for Minecraft 1.21.1 and NeoForge, including changelogs, required dependency/version changes, known regressions, removed APIs/configs, and existing pack patches. Prefer stable compatible bugfix/security releases; do not upgrade the game/loader, switch platform or introduce beta/alpha versions merely because newer. For intentionally prerelease-pinned mods, compare appropriate release channels and flag risk.
- Routine compatible updates are desired, but reconcile dependency groups, hashes/index, manifest/provenance, and relevant compatibility tests via the designated integration writer and reviewed PRs. Preserve the last tested immutable baseline and a rollback path. Hold breaking, unverified, unavailable or risky candidates rather than silently changing them. Record current/candidate version, decision (update/hold/up-to-date/unknown), rationale and tests for each changed or held mod; report source lookup gaps explicitly.
- Run quick CI and read-only integration preflight after any accepted pin changes, then freeze the resulting exact SHA for the explicitly authorized build. A full-build request covers this preflight review, not an automatic retry, unrelated build, silent major migration or unapproved scope reduction. Never move an already-authorized frozen SHA without following the dispatch authorization contract. Update review does not authorize a full build by itself. No unattended updates or new build triggers.

## Preferred owner-authorized connector dispatch

After installation, use [command console #291](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/291) for individual, explicitly owner-approved agent-driven requests. Post a **new standalone** comment `/tmm smoke <40-hex current integration SHA> <32 lowercase hex unique nonce>` for Assembly + Server Boot Smoke only, or `/tmm prism <40-hex SHA> <32 lowercase hex unique nonce>` for Assembly + Server Boot Smoke + Prism QA Package after smoke passes. Prism requests must explicitly authorize the required server smoke, too; a packaging-only request does not authorize a game boot. For incomplete test candidates obtain explicit approval of all ready-feature omissions before either command. Do not post actual build commands to test the bridge; `/tmm check <40-hex SHA>` is non-dispatch validation. The console validates the exact owner ID, new unedited comment, current integration HEAD, green exact-commit quick CI, no active full runner, and a fresh atomic nonce claim, then sends the existing launcher a normal authorized `workflow_dispatch`. No PAT or secret needs to be supplied by the owner. Receipt tags `qa-request/*` are provenance only, never server-tested/candidate/stable tags. Check the downstream run, don't confuse dispatch receipt with PASS. Never retry/replay or change the requested SHA without fresh explicit approval. Ordinary changes, other comments, and PRs remain quick-only. See [dispatch contract](docs/QA-DISPATCH-BRIDGE.md).

## Owner approval required before any full Minecraft server smoke

- **By default, do not run a full modded NeoForge server smoke test.** Routine development checks are source/manifest/packwiz/quest/config validation, syntax checks, Java compilation and unit tests. Label these `QUICK CHECKS` or `STATIC/COMPILE PASS`, not `server-smoked`.
- **A new, explicit owner instruction is required for each full server smoke run.** Completing a feature, opening/merging a PR, updating the test branch, preparing a test build or test plan, checking build readiness, or ordinary permission to run tests is **not** approval to start a modded dedicated server.
- Agents must not manually dispatch, schedule, retry, use `workflow_call`, run `scripts/smoke_server.sh`, or indirectly trigger a full smoke via push to a legacy branch without such approval. Do not bypass this rule through alternate workflows, renamed scripts, or CI edits. Disable unguarded automatic full-smoke triggers before pushing to a branch that has them.
- The active [full integration workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/.github/workflows/full-integration.yml) defaults to fast validation/compilation. Its opt-in `full_smoke: true` input is permitted **only** following an explicit instruction from the owner for that run. Only then may CI boot the full NeoForge mod roster, freeze a server-tested integration snapshot and publish the corresponding tested Prism QA ZIP.
- Do not mark quick checks as in-game/server compatibility success, publish a smoke-tested build without the test, or promote a candidate/stable build without the established verification gates.
- Preserve the 2026-11-15 overnight test already in progress; **do not cancel or restart it**. This rule governs subsequent invocations.

When in doubt, complete the quick checks and report that the full smoke remains **NOT RUN — OWNER APPROVAL REQUIRED**. This instruction supersedes any older text in historical workflows or documentation suggesting an automatic full boot after each change.

## Rolling unstable QA download (owner decision, 2026-11-17)

The [permanent unstable QA asset contract](docs/UNSTABLE-QA-DOWNLOAD.md) permits automatic **publication only** of an already successful, owner-authorized canonical Prism launcher artifact to the `unstable` prerelease. It does not authorize any additional builds or smoke retries. Preserve frozen provenance and the last valid download on build failure; old assets retained. Personal QA preference hooks are intended for this unstable testing channel, with no actual saved options/keybinds or worlds; remove them from any stable release. Never use the unstable channel to promote stable or claim client/gameplay acceptance.

## Mandatory three-type QA handoff (owner standard, 2026-11-17)

Use the [A/B/C execution standard](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/qa/QA-EXECUTION-TYPES.md) in every test-build handoff: **A Codex/offline** file/JAR/log reads, copied saves and non-game static/unit/compile checks; **B in-game command tests** with exact verified commands, mode/permissions, expected output and cleanup; **C in-game play/setup** requiring meaningful manual actions, real mechanics, UI or multiplayer. These are execution categories and complement the eight testing levels, not alternative claims of test evidence. Lead the owner with A results and blockers before assigning B/C. Preserve past evidence and only repeat previously accepted unchanged cases when dependencies/behavior warrant. Link the per-build checklist and result ledger from the QA hub. Never invent commands, mark offline evidence as gameplay success, or use QA documentation to authorize a new assembly, smoke or build.

## Continuous integration and temporary branch lifecycle (owner policy, 2026-11-19)

Read [Branch lifecycle and integration authority](docs/BRANCH-LIFECYCLE.md) before creating, resuming, handing off, or retiring a branch. This extends the existing single-writer and Progression ownership rules, not the QA/build authorization rules.

- Search and reuse before branching; one designated writer and one existing workstream/PR per coherent change. A dead chat is not a new workstream. Every temporary branch must acquire a draft or ready PR within 24 hours; record its owner, scope, dependencies, exact checkpoint, quick checks and next action. Unimplemented ideas belong in Issues.
- Ship completed, independently safe slices continuously. The designated Integration writer may review and merge already owner-approved scope (including policy/metadata and configuration-only work), reconcile shared files and frozen sources, and close superseded PRs once preservation is verified, without asking the owner again for each routine merge. No new design/balance decisions, scope expansion, full assembly/boot/package, stable release or unreviewed remote deletion are delegated. Preserve subsystem writers and required quick checks.
- Use the PR's draft state and explicit handoff status accurately; SOURCE READY is not gameplay acceptance. A task is not finished administratively until its temporary ref is retired or its retention/dependency is recorded. Do not leave parallel historical donor refs as permanent branches.
- Permanent branch allowlist: `main`, `test/full-integration`, `dev/progression`, `dev/art`. New permanent branches need owner approval. Other existing refs are not implicitly authorized for deletion. Soft total remote branch budget: healthy <=20, review 21–30, maintenance >30. Review after 24h without PR, 24h ready awaiting review, 72h without development activity, 24h after merge with surviving ref, or 7d unresolved external donor. Age alone never authorizes deletion.
- Daily branch inventory and per-PR collision checks are read-only/advisory. The reusable retirement runner accepts only a new independently reviewed exact-SHA batch on main; execution is a separate explicit owner-authorized manual dispatch or new standalone command on retirement console #359 (exact reviewed path, SHA-256 digest, fresh nonce), never scheduled. Do not use execution commands to test the bridge; read-only retire-check is allowed. Agent must obtain explicit consent for each exact batch; verify actual results and never replay uncertain requests. Keep the historical 46-branch workflow/manifest intact. Native meaningful-merge head deletion is allowed only after dependents and source provenance are safe.
