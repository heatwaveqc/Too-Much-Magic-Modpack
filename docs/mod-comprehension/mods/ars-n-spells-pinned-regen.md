## Converting gear contributions

`EquipmentIntegration.recomputeFor` runs server-side with Iron's present; disabled mana integration clears addon modifiers. respectArmorBonusesfalse clears bonuses except Hybrid's required ceiling path. ISSprimary applies Ars gear max/regen to Iron's. ARSprimary synchronizes Iron's ceiling to Ars's real maximum; Iron's gear folds into Ars through `ArsManaCalcHandler` when enabled. Hybrid synchronizes ceiling and optionally applies Ars regen gear to Iron's. Separate clears these cross-equipment modifiers rather than treating both pools as one maximum.

Equipment snapshot iterates actual vanilla equipment slots, item attribute modifiers and enchantment modifiers; optional Curios API modifiers only contribute when configured. Addon-owned modifier identities are excluded to avoid reading its own feedback into the next computation. Enchantment IDs are excluded when respectEnchantmentsfalse. `gearContribution` uses attribute evaluation with snapshot/identity exclusions rather than blindly summing every modifier; an item registered as Curio does not itself prove it contributes a supported attribute.

For ISSprimary, Ars maxMana contribution×ArsToIron conversion becomes transient ADD_VALUE `ars_n_spells:ars_gear_max_mana`; regen contribution goes through ManaRegenBridge. `ArsManaCalcHandler` only folds native Iron's gear max/regen into Ars in ARSprimary with armor bonuses enabled: max rounds after directional conversion and floors at0; regen adds converted contribution and floors at0. After Ars MaxManaCalc it coalesces/schedules server ceiling synchronization and checks mode/player again. Hybrid is a different path, not the same inverse event folding.

`EquipmentHandler` marks dirty on relevant changes and recomputes when dirty or each20ticks; potion reconciliation runs each server PlayerTick.Post when Iron's is loaded. Login invokes mode cleanup/reconciliation; capability resync also recomputes. A visual equipment change isn't proof all effects are applied synchronously in the same frame.

## Maximum synchronization and native regeneration writes

`SharedPoolCeiling.modifierAmount` computes nonnegative shortfall ArsMax−nativeIronMax divided by additive amplification (invalid factor→1), so this modifier raises a low Iron's ceiling rather than forcibly reducing a larger native maximum. `EquipmentIntegration.syncIronsMaxToArs` evaluates native modifiers excluding addon-owned IDs before applying correction. Hybrid `ensureSharedPoolCeiling` only acts when current Iron's maximum is below positive Ars real max. This is intended to avoid destroying shared mana on native max clamps; exact modpack attributes/ceiling changes still need acceptance.

`MixinManaCapability` redirects ordinary server Ars current/max/set/add/remove calls in ISSprimary/Hybrid to authoritative Iron's while scoped native access bypasses it. Hybrid's Ars view limits current to cached Ars native maximum and returns that maximum, not necessarily the entire Iron's pool. During scoped native Ars regen tick, intercepted addMana does **not** forward income; explicit nonregen grants do. Native ManaCapEvents playerOnTick HEAD/RETURN establish that scope. This suppresses one native regen stream, rather than doubling both unconditionally.

`MixinIronsMagicDataMana` redirects ordinary server Iron's reads/writes to Ars only in ARSprimary; guarded native reads bypass it. Native regen is wrapped in `IronsRegenScope`; during that scope, a proposed setMana **below current routed value** is suppressed to avoid a downward clamp. The wrapper doesn't itself discard every positive Iron's regeneration write. CastValidationScope/CrossCastContext overrides affect resource checks separately from actual native storage. Native regen and ordinary explicit grant must therefore be tested separately in each mode.

## Conversion formula and timing discrepancy to measure

`ManaRegenBridge` defines Ars absolute-rate→Iron's attribute as `A / (IronMax × .01)`; inverse is `R × IronMax × .01`. EQUAL_EFFECT uses current Iron's maximum, REFERENCE_POOL configured fixed maximum (default100), DISABLED contributes0. Both directions multiply cross-system regen multiplier; callers also apply directional mana conversion. Zero/invalid maximum yields0. These functions describe the addon's arithmetic; their parameter names/commentary are not measured per-second rates.

Pinned Iron's3.16.3 `MagicManager.tick` calls regeneration when server tickcount%10==0. `regenPlayerMana` requests `int(MaxMana) × regenAttribute × .01 × nativeManaRegenMultiplier`, clamps to0..max and writes mana. Native ServerConfigs default manaRegenMultiplier is1.0. Thus at20TPS, away from full cap and without other hooks, this formula executes twice per second. Composing the addon's nominal absolute-per-second conversion with this native cadence predicts **2×A×nativeMultiplier per second** for the transferred attribute (plus other contributions), not automatically A. Treat this as a code-derived timing discrepancy requiring a measured pack test, not a proven balancing fix or permission to modify configs. At max, event cancellation/attribute changes/client timing can obscure it; record deltas in a below-cap interval and current values.

## Potion and passive Source proximity branches

`PotionContributions.reconcile` redirects only in ISSprimary with integration enabled, otherwise removes its two modifier IDs. Native Ars `mana_regen` **and** `mana_boost` effects each contribute `.5 × (amplifier+1)` to nominal regen conversion; mana_boost additionally supplies`10 × (amplifier+1)`max bonus before directional conversion. Both effects can contribute. Effects are looked up by registry IDs; missing effect produces0. This does not prove0.5actualmana/sec independent of the native timing above.

`RegenSynergyHandler` runs server PlayerTick.Post only when Iron's loaded/integrationenabled/enable_source_jar_synergytrue. It scans **block tag membership**, not source capability fill. Exact scan: horizontal±radius (default4,hardclamp1..8); Y−1..Y+2 clipped to build height. All required scan chunks must be loaded; otherwise skips/clears cache and grants no boost. First matching `ars_n_spells:source_jars` tagged block suffices. No stored Source check/debit or cumulative multiple-jar multiplier appears in this branch: an empty tagged Jar qualifies by this condition.

Cache stores position, dimension, radius, taggeneration and gameTime. Refresh when missing/dimension/radius/generation/movement>threshold²/intervalexpired; defaults scan20ticks and movement4blocks. Backwards time also expires. Tag update, dimension change, logout and server stopping invalidate. A stationary player doesn't force rescanning every tick, and the cached hit may briefly survive block removal until refresh.

Each qualifying **tick**, `SourceSynergyPolicy.income(rate,1)` gives rate/20, where rate=ArsToIronConversion×sourceJarSynergyMultiplier (default1×5). It sets authoritative bridge mana to min(current+boost,max). At20TPS the default request is5mana/sec per player, independent of scan interval, with no Jar-fuel deduction in this handler. Legacy per-scan multiplier migration rescales by20/oldinterval; don't apply it again to new per-second values. Max configured multiplier2000 doesn't bypass recipient ceiling/cancel logic. This is a block-proximity passive loop, distinct from consuming Source or ManaWell's area ritual.

## HUD is a view, not pool proof

`ManaBarController` cancels matching namespace/layerpath containingmana: ISSprimary hides Ars overlay, ARSprimary hides Iron's; Hybrid hides whichever isn't selected by hybrid_mana_bar(defaultirons). Separate/disabled do not use this hide rule. Broad path matching isn't proof every other mod overlay is compatible. `ManaBarVisibility.shouldHideContextualBar` additionally requires contextual setting, no held casting item, finite nonnegative max and syncedintegerMana≥integercastmax; fractional rounding at full boundary is a UI case. Parent native/client screen acceptance remains unrun. Switching displayed Hybrid bar does not change authoritative pool.
