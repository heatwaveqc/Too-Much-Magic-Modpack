## Acquire, deploy, equip, recover

Use Dictionary of Spirits **Familiar Rituals**, named familiar entry/pentacle and exact ritual recipe from crosswalk. Native summon_tamed path assigns Familiar owner when caster exists. Casterless automation is not proof of ownership. Base entity also permits interacting to claim a null-owner familiar; empty main-hand owner interaction toggles sitting. Native removeWhenFarAway=false avoids ordinary distance despawn; chunk unloading still stops live AI.

Base FamiliarEntity every10 level ticks adds its familiar effect list to resolved owner at strict distance<8. This method itself does not check sitting or familiar-enabled setting; do not assume disabling every feature removes every already-applied/world aura. Effects often last300ticks and can linger after departure. Individual special effects and equipped rings have their own guards.

Craft Familiar Ring using named binding recipe. Capture server IFamiliar whose owner is player or null into an empty ring; serialize entity, stop riding/eject passengers, remove world entity. Occupied ring stores data/name. Equip in an actual **Curios slot**, not merely ordinary inventory, for ring operation. Its curioTick verifies stored familiar owner is wearer; every20 wearer ticks applies effects only when enabled, then calls familiar-specific curioTick. Thus equipped effects are not identical to all world AI jobs.

Use ring on a block to release; helper restores entity at using player's position and reassigns familiar owner to that player, then clears stored familiar. It does not compare original owner in that release helper. A transferred ring can change ownership on release. Spawn-add success is ignored before clearing data: protection/rejection can lose a familiar; no refund is proven. Test captured data, ring transfer, rejected spawn and cross-level persistence before teaching this as safe transport.

`FamiliarUtil` event lookups prefer equipped familiar, then a live same-owner world familiar in owner-box inflated10. getAll combines both. That helper's nearby range10 differs from base aura distance8 and ring20-tick cadence. Enabled checks are caller-specific. No blanket FTB-team or all-allies permission is established.

Ordinary familiar death prepares Soul Shard with max-health/reset-fall/cleared-effects entity payload, gives it to Player owner when available, otherwise drops it. Guardian/Headless have custom recovery paths. Named Resurrection/Great Resurrection use the shard activation; consume it before loading entity, spawn and reassign eligible owner. A generic empty shard is not a guaranteed pet reconstruction. Acquisition, recovery item and actual live restoration are separate quest stages.

### Blacksmith resource and timing details

Feed owner Blacksmith Iron ingots/blocks while below configured maximum. It shrinks offered stack first and then tests whether the remainder is tagged Iron Ingot to choose+1 vs+9: the last ingot's empty-stack identity can select+9. Preserve this as a code boundary requiring actual ItemStack test; do not teach overfeeding as balanced intended behavior. It does not simply accept any metal currency.

UpgradeGoal searches same-owner IFamiliar with canBlacksmithUpgrade, requires stored iron≥18 native, and post-decrements cooldown only when earlier short-circuit conditions pass.400 is not necessarily elapsed ticks while no eligible target/funding exists. Once close and upgrade valid it calls target upgrade, debits18 and triggers advancement. Guardian uses repeated upgrades for lives; others generally single upgrade. A filled ring is not a walking target in that world search.

Familiar settings, same-owner filtering, multiple effects/slots and role-specific interactions can change practical combinations. Paired Fairy+Guardian are not interchangeable: Fairy protects other familiar deaths, Guardian protects player deaths at life cost. A statically observed revive handler is not verified survival insurance.

## Spirit Fire, chalk and Otherworld tools

SpiritFireBlock entityInside only handles matching ItemEntity recipes: discards original entity, assembles result, drops stack and plays sound. `SpiritFireRecipe.assemble` sets result count to **input ItemStack count**, rather than multiplying the configured result count. Native conversion is stackwise one-for-one; invalid item simply has no matching conversion in this method. No successful spawn/refund check. Test unexpected items, whole stacks and protective hooks before building an automatic fire converter.

Chalk use places matching glyph on top/survivable or replaceable position; same chalk type reuse does not damage chalk. Otherwise survival damages chalk1 unless unbreakableChalks config. Brush+shift removes existing glyph. Method returns success even when placement branch does nothing; feedback alone is not pentacle validation. Every advanced ritual still needs exact chalk type/layout from native guide.

OtherworldPickaxeItem and InfusedPickaxeItem both report IOtherworldTool harvest tierTWO. Neither name establishes a different harvest gate on its own. Actual Otherworld reveal/loot/ore handling belongs to shared hooks and effective tags; standard tool mining tier and supernatural harvest tier are separate. Advanced chalk recipes and Otherworld loot handlers are now covered by crafting/guide and storage/harvest companions.

## Exact Chimera, Goat/Shub and Headless follow-through

Direct pinned classes, including every inner sibling, were re-extracted before CFR review to resolve an initially unavailable Headless anonymous goal. Sources: `ChimeraFamiliarEntity`, `ResizableFamiliarEntity`, `GoatFamiliarEntity`, `ShubNiggurath{Familiar,Spawn}Entity`, `HeadlessFamiliarEntity`, `util/FamiliarUtil`. Whole-JAR constant-pool scans checked references to hasGoat, isFullyRebuilt and setHeadlessDead. No client test.

**Chimera is born with its Goat branch, not a researched two-pet fusion recipe.** finalizeSpawn sets hasGoat=true, size0 and random appearance flags. Owner Golden Apple consumes1, removes attached goat flag and spawns separate Goat at Chimera position with owner, size, ring/beard appearance; actual spawn success is unchecked. A whole-JAR hasGoat reference search found only Chimera logic and client model, so do not promise an attachment/fusion operation from an independently summoned Goat. This narrows the prior “combination” research placeholder.

Meat-tag food while size<100 consumes1, adds food nutrition to size and heals4; this branch has no owner check of its own. Resizable base clamps byte-valued size0–100 and scale is1+size/100. Server random chance0.0001 per tick shrinks size1 (native expectation10000ticks per decrement, not fixed lifetime). Size adds attack damage `3*size/100` and movement speed `0.08*size/100`; size<=80 ejects passengers. Owner may mount only size>80, not sitting, not already a vehicle, and not secondary-use. Feeding large nutrition values passes a byte cast before clamp, a boundary for unusual modded food rather than an assumed unbounded growth route.

Chimera attacks choose Lion/Goat/Snake uniformly from available branches; removing Goat leaves Lion/Snake only. Lion sets remaining fire80ticks; Goat knockback2; Snake Poison200ticks. Melee damage uses Player owner attribution where applicable, otherwise mob attribution. Ranged goal uses owner cast to Player; null/nonplayer cases should not be advertised as supported. Target selection inherits familiar owner-enemy logic, not “attack everything nearby.” Exact riding/jump and cross-mod targets remain gameplay checks.

**Goat transformation:** owner feeds black dye tag, Ender Eye and Flint while either player or Goat biome is in transformation tag; each valid feed consumes1 server-side even if repeating an already-set flag. After all flags, new Shub copies ring/beard appearance and owner, position/name, then original Goat is removed after unchecked addFreshEntity. No arbitrary biome promise; effective tag membership matters.

Shub server tick calls spawn creation regardless of sitting check in this method: timer starts200 and postdecrement `<0` creates a support entity then resets200 (202 calls between creations under this direct counter). Support has6health, damage attribute6, speed0.3, creatorUUID and lifeTicks400; server postdecrement expiry or periodic detected enemies calls explode. This “explode” method directly damages selected living enemies and kills support; it does not invoke terrain explosion in this method. Lifetime/creator persist to NBT; creator resolves only a currently loaded entity in ServerLevel.

Crucial `FamiliarUtil.getOwnerEnemies`: only owner's last attacker and last attacked entity are considered; null owner yields empty. `isClose` compares **distanceToSqr < range**. Calls passing10 therefore use distance<sqrt(10), not a10-block radius. Same entity can appear twice when it occupies both references; list is not deduplicated, so damage can be attempted twice, subject to hurt/immunity handling. It is not blanket hostile-mob AoE. Shub's support damage is attributed to owner when nonnull. Shub can ride Cthulhu; bypasses-armor immunity check while riding is method-specific, not universal invulnerability.

**Headless:** damage method calls superclass then, if remaining health/maxhealth<0.5 and not already disabled, marks headless-dead. This is a disabled familiar state, not normal entity death. Attack goal checks that flag. Head timer1200 expires its copied species; upgraded active Headless every10ticks gives Weakness60 to matching head-type entities in box inflate5 excluding owner.

While disabled, interaction rebuilds six bit flags: Wheat-tag item1 per left/right leg (two total), Hay Block1 body, wooden rods1 per left/right arm (two total, body required), Carved Pumpkin1 head (body required). This branch has no owner check of its own and shrinks successful inputs. All six flags (byte63) trigger HEADLESS_REBUILT advancement. **Pinned body does not clear headless-dead, restore health or reset rebuild flags on completion.** Whole-JAR reference scan finds isFullyRebuilt/setHeadlessDead only in this class; its false assignment occurs in loot/shard serialization, not rebuild completion. Therefore present the interaction and advancement as source-known, but do not promise that spending materials restores working combat in this version. Runtime observation may distinguish additional engine/event behavior; none is asserted here.

On true loot/death path, Headless resets health/effects/fall, disabled=false and rebuilt0 for Soul Shard serialization, then restores original health and delivers shard to owner/drop via native code. Resurrection remains a different recipe route, not proof that the six-item rebuild repaired the living disabled entity. The finite rare branches above replace the old fusion/rebuild speculation; parent native progression and utility helpers are now consolidated.


## Residual utility familiars and their actual upgrade actions

The remaining major utility helpers were checked against the same pinned classes, including all nested goals. Sources: `BeaverFamiliarEntity{,ChopTreeGoal}`, `CthulhuFamiliarEntity`, `GreedyFamiliarEntity{,FindBlockGoal,FindItemGoal}`, `BeholderFamiliarEntity{,RayGoal,EatGoal}`, and already-audited `FamiliarUtil`. These close the old table's method-level placeholders; gameplay/pathfinding/protection tests remain separate.

**Beaver:** owner empty-hand nonsneak interaction after Blacksmith upgrade produces Beaver Nugget when gameTime>lastSnackTime+20, updating timestamp. No payment ingredient in this branch; before upgrade it reports no-upgrade. This is a native food route (food nutrition8/saturation modifier0.8), not an invented tree-loot conversion. Tree-growth hook's target assignment is separate from chopping. ChopTreeGoal requires not sitting, effect enabled and target log. It navigates until squared distance<=4, then traverses nearby log positions using withinManhattan(1,1,1), tracking a set capped by loop condition size<15. If queue remains when loop stops it clears target and **does not destroy the accumulated set**; it is not an unlimited tree-feller. If traversal drains, destroys collected blocks with drops, clears target and fires BEAVER_WOODCHOP. Native duplicate queued positions/connected logs mean “exactly15-log maximum accepted tree” is too strong; use a small isolated grove and verify actual result.

**Cthulhu:** owner feeding one Lapis-gem-tag item after strict gameTime>lastPrismarineTime+60 produces one Prismarine Shard normally, or random1–4 after Blacksmith upgrade (`nextInt(1,5)`, upper bound exclusive). Both branches consume1 and set timestamp; upgrade is a yield change, not first access to the trade. Upgraded world entity periodically places LIGHTED_AIR only when its current block position is empty and entity alive. It removes tracked previous light on update/removal; no arbitrary solid-block overwrite in this helper. Position tracking/teleport/dimension cleanup still warrant actual observation. The helper checks current upgrade at placement; this is not a permanent bound light service after losing/releasing the familiar.

**Greedy:** owner sneak-interact opens filter menu. In upgraded nonempty-offhand retrieval branch any interacting player can be given the held item in that method; similarly feeding a BlockItem into upgraded empty-held state has no explicit owner check in its branch and spends1. Do not teach a private locked container. FindBlockGoal searches configured horizontal/vertical ranges for block identity matching offhand sample, sets visible target and moves there; it does **not mine/break** that block in this goal. Thus locating a sample block is distinct from obtaining its drops.

FindItemGoal scans alive ItemEntities in familiar box inflate12, needs Player owner, respects PreventRemoteMovement, Greedy's item/tag filter and simulated player-main-inventory capacity. Navigates and within squared distance<4 invokes item.playerTouch(owner), then fires GREEDY_ITEM even if final pickup restrictions prevent delivery. Dragon vehicle can reuse this goal when carrying Greedy; familiar type/passenger resolution is explicit, not universal shared inventories. Equipped ring path has box5 scan as already documented; physical and ring paths have different ranges. Ordinary inventory/full/remote-movement limits remain important.

**Beholder:** glow tick chooses one nonglowing nonplayer LivingEntity in owner's box inflate10 when enabled, applies Glowing1200. World/ring callers attempt this with random2% tick chance. Upgraded familiar obtains Warden-upgrade flag when that chosen entity is Warden/PossessedWarden; simply owning a Warden-themed item does not grant it. That saved flag supplies the previously documented Darkness protection branch.

RayGoal requires Player owner, targets owner's recent enemies via shared helper called with100 (squared distance<100, actual distance<10), sends attack visual and later requests9damage per recorded entity ID; Strength multiplies by amplifier+2. It does not do a fresh all-hostiles area query or claim an armor-bypassing damage type. Targets may move/disappear before resolution. EatGoal requires nonsitting and cooldown postdecrement, searches live Shub support spawn in box3; when enabled it discards one, grants StrengthI/SpeedI12000 to Beholder, fires advancement. Cooldown resets600; support consumption is not a generic mob/food sacrifice. Ray/Familiar event feedback is not proof of final damage through other mods' protections.
