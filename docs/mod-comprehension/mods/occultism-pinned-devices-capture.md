## Capture/release contracts

`SoulGemItem` capture is main hand only, target must be alive LivingEntity, server-side, never Player, empty ENTITY_DATA. Fragile/Soul/Trinity each checks **its own** deny tag when that exact item is used. It serializes the target with ID and full saved data into the item, then discards original; there is no owner check in this capture method. This does not mean every modded/protected entity is capture-safe. Bundled fragile_soul_gem_deny_list and soul_gem_deny_list include Iesnium Golem, optional #c:capturing_not_supported and #c:bosses. The inspected JAR has no trinity_gem_deny_list JSON; contributions from the effective pack may add it, so an empty native definition is not a global absence claim.

Release main-hand useOn removes ENTITY_DATA **before** validating entity type/creation. It clears Pos, loads entity, places at clicked position or adjacent face when collision exists, rotates toward player+180 and calls unchecked addFreshEntity. Fragile Gem removes itself from main hand after this call; ordinary gem remains empty. Invalid type, creation failure or rejected add has no payload rollback in this method. Test only disposable captures before trusting valuable pets/workers.

MagicLampItem capture is narrower: owned SpiritEntity with present job, main hand, alive server-side and empty lamp. It saves entity data plus job/name, discards worker. Release clears payload before validation/add, resets displayed job/name afterward, no success check/refund. Filled lamp every20ticks has1/100 random chance to send owner a spirit message, and hurts sleeping Player by1 in that branch. It is not a generic arbitrary mob container or unconditional safe storage.

## Battlefield operation and economy

Soul slot accepts any stack with ENTITY_DATA; weapon accepts ATTRIBUTE_MODIFIERS; fuel accepts SOUL_VALUE. These component gates do not validate every payload as a usable living entity in the insertion method. Output has25slots. Server tick pauses on redstone signal or missing soul/weapon; EvilCraft Unusing pauses weapon near damage max−6. Cached entity/loot rebuilds on item object changes. It creates a living entity from payload **type** for simulation; does not load every captured entity property into that simulated instance. Captured attributes may separately influence health budget.

Health budget starts at simulated max health (can read saved max-health base from payload attributes), multiplied by configured butcherLifeMultiplier; soulValue cost equals health unless soul itself has SOUL_VALUE, in which case0. Weapon sums attack-damage/speed modifier amounts (rather than universally evaluating every modifier operation), adds relevant Sharpness/Smite/Bane/Impaling bonuses and triples damage for Iesnium-knife-tag weapon against designated demon-healed types/boss tags. Derived work count is max(integer(health/damage),1); hit interval integer(40/attackSpeed). This is a simulated processing formula, not live entity DPS.

Each hit decrements work count and has configured butcherHurtChance to damage weapon1. Completion computes fuel luck component, spends fuel unless soul itself has SOUL_VALUE, with shrink `1 + soulValue/max(fuelValue,1)` (integer division). Fuel availability precheck requires fuelValue×count >= soulValue, so exact divisibility can still request one more unit than that ratio; shrink handles available count. Spending occurs before defeat's failure check, so Fragile Gem's80% failure does not refund work/fuel. No FE/fluid input in this operation.

Defeat uses soul ROLLS_PER_OPERATION default1; bosses force1, possessed types reduce rolls and may switch to base mob. It then **overwrites passed fuel luck with min(rolls,16)**, adds integer(luck²/100) rolls and a probabilistic fractional roll. Thus adding a luck-valued fuel does not straightforwardly increase this method's final luck as its parameter name might suggest. Soul consumption chance is optional CONSUME_CHANCE/luck; defaults0. The native Soul Gem can be a reusable template unless changed by components/config/hooks.

Loot lookup first tries `occultism:battlefield/<entity namespace>/<entity path>`, falls back to ordinary entity loot if empty. Evaluates loot with a cached FakePlayer, equipped weapon/tool, owner-like attack context and luck, then posts LivingDropsEvent for each roll; canceled events emit no output. Item insertion remainders into current output destination are **ignored**, including generated XP bottles, so full/rejecting output can lose loot after costs. Extractor directly below selects UP-face destination two blocks down when present, otherwise internal output; it does not make insertion transactional. Captured XP orbs within squared distance1 during listener window increment xpStored; >9 stored converts tenXP per Experience Bottle before adding current simulated XP reward. SaveAdditional serializes inventories, not a guaranteed persistent complete combat-progress/XP state; acceptance must verify reload behavior.

## Stable Wormhole, Entity Wormhole and satchels

Additional exact classes: `block{,/storage}/{EntityWormholeBlock,StableWormholeBlock}`, corresponding block entities, `item/storage/{StableWormholeBlockItem,SatchelItem,EnderSatchelItem}`, `item/tool/ritual_satchel/{RitualSatchelItem,SingleBlockRitualSatchelItem,MultiBlockRitualSatchelItem}`. Recipes and Dictionary entry paths are in the complete crafting/ritual/guide tables. These systems are optional choices with distinct actions; no generic backpack/logistics mod is added or endorsed by documenting native content.

**Stable Wormhole is a storage proxy.** Sneak-use its block item on an IStorageController to record GlobalBlockPos (also updates existing block-entity payload when present), then place. Unlike Storage Remote's any-use link, this item explicitly checks sneak. Block entity resolves a controller only when its location is loaded; missing/wrong linked block clears link server-side and sets LINKED=false. It shares controller storage/menu behavior, not a second independent capacity pool or entity teleport. Saved implicit link components support the block-item link path; acceptance should verify break/place and cross-dimension load boundaries.

**Entity Wormhole is a portal destination device.** One internal slot accepts compass-tag item and limit1. Use compass on empty slot inserts it; sneak-use removes current compass; Spirit Attuned Gem in main hand cycles exit Y rotation, offhand cycles X rotation, without consuming gem in that branch. Entity entering must be nonspectator, canUsePortal(false), intersect block shape or be Projectile, and compass slot nonempty. Destination is computed at travel, not from a universal paired-portal network.

Destination priority: Lodestone Tracker component target→its dimension/position above; otherwise vanilla Compass→current dimension shared spawn unless custom name exact `RTP` requests configured random destination or exact `HOME` for ServerPlayer resolves valid bed/charged respawn-anchor stand-up position. Recovery Compass uses ServerPlayer's last-death dimension/position. A compass-tag item with SPIRIT_ENTITY_UUID can target that loaded entity across server levels; no matching loaded target means no resolved destination. These are exact branch conditions; custom compass compatibility is not automatic.

Nonprojectiles try native safe-position helper around target before failing; projectiles use target bottom center. Successful DimensionTransition retains velocity, uses configured exit orientation or existing entity rotation and requests portal sound/ticket. This is no universal safety guarantee in arbitrary dimensions/modded collision shapes. RTP retries configured maxTryRTP, chooses offset bounded by world border and maxDistanceRTP, searches vertical support, rejects bottom/water/lava cases; range-zero/random bounds, inaccessible terrain and full collision must be tested rather than declared safe. Base portal supports moving entities, not just players, subject to native portal allowance.

Fishing hook optional pull: RightClickItem with FishingRodItem, uncanceled server event, existing hook with no hooked entity and exact zero velocity located in EntityWormholeBlock calls pullEntity. It looks for the compass's SPIRIT_ENTITY_UUID in loaded server levels and teleports that nonspectator portal-eligible entity to portal bottom center; this pull path does not use the same target safe-position search as ordinary travel. Do not promise all pets or unloaded entities can be recalled. This source audit does not implement player teleport commands or replace TMM travel gates.

**Backpack Satchel** opens item-backed117-slot inventory on use, creates SATCHEL_UUID if absent, records selected main-hand slot or offhand−2 for menu. It is native storage content, distinct from the two ritual construction satchels. Its capacity is not evidence of generic backpack approval or a new addon request. **Ender Satchel** nonsneak opens Ender Chest inventory; sneak toggles linking to current player's UUID/name. When linked player resolves in loaded server levels it opens that player's Ender Chest; if unresolved, code initializes/falls back to current user's Ender Chest while stored name may remain. This is not offline cross-player access guarantee. No owner-only rebind restriction appears in this item method; don't present transferred linked item as private ACL.

**Ritual satchels** use item-backed36-slot inventory. Main-hand sneak-use opens menu; offhand passes. Load actual construction blocks and ChalkItems, use native Modonomicon pentacle preview to set target; then nonsneak-use places. Target PentacleData must match player UUID/clicked position and be at most5game ticks old, then server re-simulates multiblock. T1 tries one matched position; T2 iterates simulated positions and can partially place whatever materials fit. It is not an all-or-nothing transaction or a way to create pattern materials for free.

Placement helper rejects Any/DisplayOnly matchers, requires replaceable above-position for T1 or clicked-position for T2, finds BlockItem/ChalkItem whose placement state satisfies matcher, avoids exactly one durability remaining and checks glyph survival. It calls actual stack.useOn and writes stack back. **The returned useOn result is not inspected before helper reports SUCCESS**: an attempt can appear successful even if underlying placement refused, so verify resulting blocks/pentacle.validate rather than trust return alone. Incomplete inventory, support/collision and remaining chalk durability are meaningful boundaries.

T2 use on supported ritual center bowls/chalices instead collects validated pentacle materials: obtains current ritual multiblocks, validates/simulates, skips Any/DisplayOnly/air/non-PENTACLE_MATERIALS, calculates block drops, sets matching world positions to air, inserts drops in36-slot satchel and gives remainders to player. It collects actual drops (not guaranteed original items), may process multiple valid matching patterns, and is not a universal undo of ritual sacrifices. No block protection bypass is claimed; external hooks and critical center contents require disposable acceptance. Use a dedicated ritual area, never assume this is harmless near valuable structures.

Positive/boundary handoff: native item/link acquisition; loaded/unloaded controller; compass destinations and safe obstruction; no UUID target; offhand vs main gem orientation; ritual preview freshness, material shortage and refused stack.useOn; collection with occupied center/full satchel; Ender Satchel linked player online/offline and transferred item. All unrun. Parent walkthrough and residual utility/trader helpers are now consolidated; these optional devices are source-mapped, with the listed acceptance checks separate.
