## Guide and setup

The native Compendium explicitly registers **Power Consolidation**, **Caliburn** (two continuation sections), **Morgan**, and **Morgan (cont.)**. The Power Consolidation page receives configured lake/sword costs; Caliburn/Morgan ability pages receive the translated Change Mystic Code key. JEI has dedicated `CaliburnJeiRecipe` and `MorganJeiRecipe` records, but viewer rendering and category wiring still need client acceptance. An enchanted-book icon or entity display in that viewer is not itself a consumed book or spawned output.

This is an optional weapon branch, not a prerequisite for ordinary spells. Supply two Powdered Diamond and one Powdered Emerald for the native **Power Consolidation** recipe. Its registration does not require cloth; use the stationary floor circle to create the lake. Keep the basin away from builds, containers and protected land until terrain/protection tests pass. The later sword conversion requires a substantial5,000 mana payment; an early personal maximum100 alone is insufficient. Charged gems/circuits can supply the ordinary payment helper.

## Lake construction and exact cost

`PowerConsolidationMahoujinTileEntity` uses the shared server ticker, cycle20. Starting from saved `numTimesLaked=0`, it pays30 per successful growth, increments that count, and removes its own circle on a later cycle when count≥`radius−1`. Native radius12 therefore permits **11 paid growth calls:330 total mana if all execute**. This is not twelve payments. First work is on the21st ticker invocation from counter0; subsequent opportunities are20 invocations apart. Loading/tick scheduling and interruption must be measured separately.

For each payment it tries circuits **first**, centered on the circle and authorized by caster UUID; only if that helper cannot fund the whole request does it try the caster's ordinary personal/gem/circuit payment. This differs from ordinary player spell payment order. The battery-first helper counts before draining, so a short battery pool is not partially spent by that first attempt.

Growth examines a sphere-like region below the circle, skips positions with block entities, and invokes `EffectUtil.tryChangeBlockState` to form a dirt shell and Murky Water interior. A paid call increments growth even if protection/terrain hooks prevent changes. Consequently payment/count completion does not prove a usable lake exists. Full block-change helper/protection semantics remain open; this is not permission to assume bedrock or claimed blocks can be replaced.

The conversion lake recognizer flood-fills face-connected `MurkyWaterBlock` positions. It succeeds when the collected count is **strictly greater than150** by default, so150 is insufficient and151 qualifies for that numeric guard. It can stop early once sufficient; this is not a full-lake geometry validation. Do not teach a particular hand-built basin footprint without a tested build reference. `findCenter` uses the inspected set's X/Z bounds and highest Y, so the eventual weapon position need not be exactly the dropped sword position.

## Sword conversion and re-consolidation

1. Complete a functioning lake and prepare an **enchanted allowed `SwordItem`**. Default blacklist excludes `mahoutsukai:clarent` and `mahoutsukai:morgan`; blacklist mode is true. It compares exact item registry strings, not a universal sword tag. The projected-item exclusion in this path specifically checks projected Caliburn when projections are disabled; do not generalize it to every projected sword.
2. Ensure the dropped ItemEntity has a **Player owner** and is in Murky Water. An ownerless input receives a help message and is not eligible. Actual player-drop/automation ownership needs testing; a hopper/dispenser route is not established.
3. Ensure any configured Mandatory Fun gate is met. Native `CALIBURN_FUN_REQUIRED=false`, so its ten configured activities do not block the default route. If enabled, the helper tests the configured named requirements against the player's saved completion map; missing requirements can give a Fun book when inventory has room. Those optional activities need their own emitter walkthrough before enabling that gate.
4. Keep at least5,000 permitted mana available. The server world handler checks every20 game ticks by default, scans ItemEntities and verifies enchantment, ownership, allowed item, lake threshold, optional Fun gate and `hasMana` before constructing a candidate.
5. The handler computes innate cap from nearby upgrade offerings and attack from the input, then queues a server action. At that queued action it rechecks input alive/Player owner and demands an actual5,000 return from `drainMana(..., false, false)` before adding the weapon projectile and discarding the input. Resource availability at the preliminary check does not reserve payment.
6. Retrieve the resulting Caliburn weapon projectile after it embeds. `WeaponProjectileEntity.playerTouch` accepts a server-side touching player when in-ground, copies one weapon, applies2 durability damage and adds it to inventory; it discards the projectile only if inventory insertion succeeds. No owner-equality check appears in this pickup override. Full inventory leaves it in-world. Its lifetime counter discards it after3600 ticks (nominal180 seconds at20TPS); retrieve promptly and test persistence/unload behavior.
7. For further Caliburn damage, enchant the existing Caliburn and repeat the same paid lake conversion. This is another input sacrifice, not a free anvil merge. Source custom name is preserved when the input is Caliburn; general enchantments/components are not copied to the fresh output by this conversion path.

**Damage calculation:** The handler simulates an attack against a FakeSkeleton, repeats with enchantments stripped (and Apotheosis unsocketing when enabled), and applies native nerf factor0.6 to the difference. It then subtracts1 and caps the stored attack component at global attack cap5,000,000. Therefore the default retained difference is40% of the simulated enchantment bonus; it is not “all enchantment damage.” Fake-target hooks and cross-mod attribute changes can affect the simulation, so do not promise a fixed amount from Sharpness/Smite levels without tracing those hooks or testing. The stored component is an attack modifier, not measured final damage against every target.

## Innate-cap offerings and loss boundary

`getLimitBreakInArea` searches ItemEntities in an axis-aligned box extending10 blocks on all three axes from the input sword. It sums stack counts matching `POWER_CONSOLIDATION_TIER_UPGRADE_ITEM` and **immediately discards all matching entities**. Native list is Nether Star. No offering-owner or in-water check appears in that helper. Keep unrelated dropped Nether Stars away from a conversion.

Native tier list has83 entries: no offerings chooses index0/cap100, one chooses index1/cap150, two cap200, three cap250;82 or more selects the final cap5,000,000. All counted offerings are discarded even beyond the last useful tier. These counts describe the lookup, not a recommendation to feed rare items before testing. Re-consolidating an existing Caliburn preserves the greater of its old innate cap and the selected offering cap.

The offering discard and native `SWORD_IN_THE_LAKE` trigger occur during candidate construction **before queued final mana payment and spawn**. The queued action does not revalidate all original predicates. If payment/input/spawn subsequently fails, this path provides no offering refund. `addFreshEntity`'s boolean is ignored before original input discard; rejected spawning can lose input/payment. These are code-supported loss boundaries requiring controlled tests, not confirmed TMM incidents or an implemented fix. An advancement is not proof the final weapon was successfully obtained.

`GrowSwordItem.getCappedAttack` clamps stored attack to innate cap and global cap when exposing Caliburn/Morgan attributes. A newly selected cap does not itself grant that much damage. Both weapons have native durability1000, disallow ordinary repair through `isRepairable=false`, block same-type weapon/weapon anvil operations, and blacklist Mending in their primary-enchantment check. Other anvil/mod repair routes require separate acceptance; do not claim all external repair is impossible.

## Morgan conversion and growth

The subscribed `MorganEffect.morganLivingDeath` requires a Player damage-source entity and reads that player's **current main-hand item at death**. With Caliburn held, it accepts a configured exact entity ID; for a `TamableAnimal`, owner UUID must match the player. Native whitelist is `minecraft:wolf`. Thus the default route is a player-attributed kill of the player's own tamed wolf with Caliburn held; other players' pets, untamed wolves and unrelated species fail these gates. The handler does not itself test that the lethal hit was a direct sword swing; actual attribution/projectile ordering needs a boundary test.

This transformation does not call an additional mana drain. It creates fresh Morgan, transfers attack/innate cap within global/innate limits and copies current damage value, then replaces the selected inventory item or drops the new item if insertion fails. General source name/enchantments are not copied in this handler. Native Morgan advancement triggers afterward. The old Caliburn is consumed by replacement; carry a separate Caliburn if pursuing the native dual-weapon secret advancement.

For growth, the same death handler accepts `AbstractVillager` targets while Morgan is held. Native upgrade cost400 mana is charged through the ordinary manager. On successful payment it repairs30 durability and increases stored attack by0.2 for an adult or1 for a baby, limited by innate cap, then triggers `BREADCRUMBS`. It uses the Java class check, not solely `minecraft:villager`; eligible subclasses and modded villager behavior need acceptance. Failed payment does not grant the damage/repair; death has already occurred. Cap does not bypass this payment check, so kills at cap can still cost mana and repair durability.

The separate `secretCalibur` player tick check triggers native `SECRET_CALIBUR` when one hand holds Morgan and the other Caliburn. It does not construct a new Excalibur item. In the pinned Caliburn class `canSwitch=false` and `getMode` always returns CALIBURN despite an EXCALIBUR enum/unused branch; do not invent a functional Excalibur progression from the enum alone.
