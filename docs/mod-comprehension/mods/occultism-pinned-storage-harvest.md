## Storage setup and limits

Follow Dictionary **Storage** and the named Matrix/Controller Base/Stabilizer/Remote entries; the ritual appendix lists bound-spirit ingredients. Craft Dimensional Matrix, create Controller Base via proper binding, assemble controller, open it and insert/retrieve a mundane test stack. This is a magic-native storage system, not permission to add generic external logistics. Teach distinct item-type and total-count limits.

Native config constructor: controller128 types/256000 total items. Stabilizer additions by tier are64/512000,128/1024000,256/2048000,512/4096000,1024/8192000. Counts are total across all types, not capacity per type. Stabilized-controller variant uses configured8 tier5 equivalents (native8320 types/65792000 total), whereas ordinary controller sums discovered physical stabilizers. Effective TMM overrides remain untested.

`findValidStabilizers` starts **one block above controller**, traces each of six directions out5, and accepts first StorageStabilizerBlock only when facing back toward search direction. `Math3DUtil.simpleTrace` includes starting position and does not test intervening opaque blocks: this is not an unobstructed-air line-of-sight ray. A first wrongly facing stabilizer can hide a farther correctly oriented one because facing is tested after first hit selection. Use native guide preview plus actual linked-capacity feedback; no arbitrary circle layout implied.

Controller first server tick initializes stabilizers. Limits setter delegates max item types/count to its handler and syncs; storage contents and matrix are saved separately. Removing upgrades/capacity reduction and breaking/replacing controller need live tests before trusting valuable items to it. Displayed capacity is not proof a specific third-party insertion/storage proxy respects it.

## Remote linking and access

`StorageRemoteItem.useOn` links **any use-on a block entity implementing IStorageController**; there is no sneaking condition or owner check in this method. Stores GlobalBlockPos and sets Rare display rarity. Mere remote possession does not prove link or access.

Server use resolves linked server dimension and tests hasChunkAt; unloaded target displays not-loaded rather than deliberately loading it. It then tests IStorageController and opens menu for ServerPlayer. No UUID/team authorization appears in these two item methods; external claim/menu/container protections require acceptance. A shared/transferred linked remote is not proven private storage access control. Missing target dimension has no null guard immediately before hasChunkAt in this path, so stale-dimension links need a boundary test.

Menu creation uses `CuriosUtil.getStorageRemote`: main selected slot first, then equipped Curios remote, then first remote inventory slot; fallback expression accepts only slot>0. Offhand/current-hand use can therefore select another remote than expected. Teach the linked remote in main hand for initial test and compare multiple remote links before recommending offhand/Curios use. This is a selector finding, not a tested theft/loss claim.

Native storage manipulation, machine-manager jobs and the Neo Vitae/Ars bridges must be traced from both sides before describing automation/permissions as compatible. Main profile's source-based setup remains useful; this appendix closes these exact pinned item/controller methods, not every GUI transaction.

## Harvesting, loot and familiar interactions

- `OtherworldPickaxeItem` and `InfusedPickaxeItem` both return supernatural harvest tierTWO. In `LootEventHandler.breakSpecialBlocks`, a noncreative Player breaking a block tagged OTHERWORLD_COLLECTS with held Iesnium/Infused pickaxe or detected staff gets one BlockItem spawn, block replaced with Air and BreakEvent canceled by this handler. Block NBT is not copied; direct state writes/spawn booleans and event ordering need protection tests. This is not a general Silk Touch on every block.
- `playerHead` can spawn victim Player Head with profile when source weapon matches Iesnium knife tag and death not canceled. Player-attributed damage vs source weapon is a different gate from familiar lifesteal. No repeatable-player farm or faction exception is authorized.
- Fracture Soul on killer LivingEntity's weapon can add Shattered Soul to LivingDrops with chance=enchantment level×configured chance. Excludes soul-shattered deny tag, IFamiliar and Player; requires encode ID. Saved payload temporarily restores victim health/clears effects for serialization. Actual boss blacklist/tag and revivable output require live loaded-tag/ritual audit; encoded entity payload is not automatically an allowed boss respawn.
- **Dragon Greed closure:** LootEventHandler only adds amplifier+1 to a nonzero experience drop with attackingPlayer carrying effect. It does not multiply ordinary item loot in this inspected handler. Thus familiar effect's name is not a guaranteed ore/boss-drop multiplier.
- **Blacksmith repair closure:** enabled nearby/equipped Blacksmith plus pickup of stone/cobblestone tag can repair the first damaged equipped/held slot by2 with probability configured0.33×ItemEntity stack count. Regardless of repair success, the event denies pickup and discards **the whole stone ItemEntity**. More stones do not give one repair per unit; full stack can be consumed for one attempt and no repair when nothing is damaged. Keep valuable building stacks away when testing.

## Storage dispatch, insertion and crafting-menu follow-through

Exact same pinned JAR; additional sources `StorageControllerBlockEntity`, `common/container/storage/{StorageControllerContainerBase,StorageControllerContainer,StorageRemoteContainer}`, `ManageMachineJob` and `ManageMachineGoal`. All nested menu classes were extracted with parents before decompilation. No runtime/security/dupe acceptance claim.

Controller insertStack rejects its four controller BlockItem variants and Storage Remote, returning unchanged count. Otherwise it simulates map-handler insertion and performs actual/simulated insertion only when something fits, returning remainder count. Callers must handle that remainder; worker extractor loss cases are documented separately. This blacklist does not imply every inventory capability path enforces an identical gate.

`getItemStack(comparator,requestedSize,simulate)` returns empty for nonpositive amount/null comparator. Component-matching ItemStackComparator takes its exact filter-key extraction path. Other predicates scan map slots; first matched stack establishes item+components, then only identical item+components can be combined into the returned stack. Thus a broad tag predicate does not aggregate arbitrary different materials into a single returned stack. `getAvailableAmount`, however, sums all matching comparator slots for the noncomponent path; displayed/request availability can span variants that one extraction will not combine. Counts are ordinary int in this method, despite larger overall storage capacity.

`addDepositOrder` only proceeds when simulated extraction finds a nonempty stack, not necessarily the full requested amount. It looks up the machine's registered spirit UUID, resolves a loaded SpiritEntity/ManageMachineJob and queues comparator+amount; no stock is reserved or withdrawn by this enqueue method. Later jobs can compete for stock. Missing job removes registration; queueing is not completed crafting/output delivery. Machine manager's saved queued orders and its capability checks are in the worker appendix.

**Menu locking is concurrency, not owner privacy.** Static openContainers map keys only BlockPos (no dimension key); canOpen allows unreserved position or same player UUID and otherwise messages “already open.” reserve records player UUID. Closing a menu updates crafting/order data and removes every reservation held by that UUID. Same coordinates in different dimensions can therefore contend if these methods are used; this is source key scope, not a tested gameplay fault. No blanket team ACL/cryptographic ownership claim follows.

Local StorageControllerContainer persists nine crafting matrix slots and order slot to controller. stillValid requires that exact controller object at position and player squared distance<=64 (eight-block distance), periodically syncing stacks and machine references every40ticks. Remote menu resolves linked controller from the selected inventory slot/Curios remote; locks its remote slot in the menu and saves crafting matrix/order stack into the remote item's own components. Remote stillValid requires resolvable controller and remote, without local eight-block distance gate; linked chunk/dimension constraints still apply as documented above. Closing saves matrix, rather than automatically returning every grid ingredient to player.

Shift-clicking ordinary menu slots tries controller insertion and keeps returned remainder in slot. Output shift-click calls craftShift. Crafting uses actual server RecipeType.CRAFTING match/assemble on the3×3 matrix; it does not execute arbitrary processing-machine recipes. craftShift snapshots the matrix, locks recipe, batches while matches/output item agrees and a simulated player-main-inventory insertion accepts each assembled result. It stops at one result max-stack count by `crafted + resultStackSize <= maxStackSize`. It handles recipe remaining-items/container branches, shrinks consumed inputs, refills emptied matrix slots from controller via most-common matching item, then gives combined result to player and refreshes recipe/sync.

Important constraints for future acceptance: per-iteration inventory simulation does not reserve space for all accumulated output (actual give occurs after loop); component-varying recipes are checked by item identity in loop but final output applies first result components while summing intermediate counts; special remaining-item branches warrant exact tests. These are source-sensitive branches, **not confirmed duplication or compatibility bugs**. Do not promise lossless generic crafting for every modded custom recipe without testing remainders, damageable ingredients, full inventory and component-specific outputs. `hasIngredient` used for client missing-ingredient display reserves counts across grid/cache; UI availability is not server transaction proof.

Remaining source closure is full ordinary recipe/guide-to-stage reconciliation, Otherworld visibility/loot branch details and residual familiar helpers. Menu packet validation, concurrent use, actual crafting/remainder behavior and cross-mod handlers remain unrun gameplay/engineering tests, not grounds to mark source analysis as runtime PASS.


## Otherworld visibility, harvest tier and divination

Pinned `IOtherworldBlock` chooses player harvest tier as maximum of active Third Eye→ONE, CuriosUtil.hasStaff→TWO and IOtherworldTool/component tier. A present `OTHERWORLD_TOOL_TIER` component replaces the tool-interface tier before maximum calculation. It sets the loot-call state `uncovered=true` only when player tier >= block tier. Seeing a client-revealed block is not an independent server harvest grant. Goggles are not checked in this harvest-tier method; use an appropriate Otherworld/Infused pickaxe or staff for tier-two acquisition.

Client `ThirdEyeEffectRenderer.onPlayerTick` runs only for local client player. It uncovers IOtherworldBlocks in inclusive ±10 block cube: Third Eye revealsONE, equipped goggles revealTWO, staff path revealsTWO. This changes client states/rendering, not a global world reveal for every player. `OtherworldGogglesItem.isGogglesItem` accepts native item class, goggles item tag or boolean goggles component; CuriosUtil checks helmet and equipped Curios. The simple ThirdEyeEffect itself has no native resource-generation tick body. Inventory item name visibility also considers IS_INVENTORY_ITEM or Third Eye through OtherworldUtil; names alone do not identify server harvest permission.

Natural Iesnium Ore is tierTWO and covered analogue Netherrack. `playerDestroy` passes adjusted harvest state into normal destroy/loot. Native loot: covered→Netherrack; uncovered + Silk Touch→Iesnium Ore; uncovered without Silk→Raw Iesnium with fortune ore-drops function. Natural Otherstone alternatives uncovered→Otherstone/covered→Andesite; natural log→Otherworld Log/Oak Log and stripped equivalents likewise. Those are loot-call conditions; separate high-tier collection event can instead yield the natural BlockItem as documented above. Silk Touch alone is not the tier-two magical permission. Effective correct-tool/block tags and external protection hooks still apply.

DivinationRodItem is a locator, not automatic miner. Sneak-use a nonair analogue to link: Andesite→natural Otherstone, Diorite→natural Otherrock, Oak Log/Stripped Oak Log/Leaves→corresponding natural Otherworld block, Netherrack→natural Iesnium, flower-tag block→natural Otherflower, End Stone→natural Otherglass. Corresponding actual Occultism blocks also link. Optional server anyOreDivinationRod permits ore-tag targets; Creative or True Sight Staff allows arbitrary block fallback. Thus “never a general ore detector” would overstate the fixed restriction: default/config and staff matter.

Stop sneaking and hold use40ticks to scan a linked target (client ScanManager); finish applies40tick cooldown, reports result to server and shows selected block for10000milliseconds or Theurgy particle integration when loaded. Early release cancels current scan and can retain previous result. Its displayed distance band ignores Y: horizontal<6→0,<15→1,<25→2,<35→3,<45→4,<65→5,else6;7 means not found and8 searching. This is neither exact 3D distance nor proof of accessible/reachable ore. Scan radius/scheduling are client-config/runtime questions; no unlimited/all-loaded-world scan claim is made.
