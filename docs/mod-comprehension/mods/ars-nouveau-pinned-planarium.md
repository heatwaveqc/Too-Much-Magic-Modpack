## What the player builds

Notebook **Crafting -> Planarium** describes naming, sneak entry, interior projection, spawn setting and boundary exit. JEI `planarium` recipe: Mob Jar reagent, Stable Warp Scroll, Conjuration Essence and Diamond on Apparatus pedestals; SourceCost0, keepNbtOfReagent=false, one `ars_nouveau:planarium`. No requirement for a filled Mob Jar or recorded Scroll in this ingredient definition; do not silently promise their old contents survive crafting. Apparatus infrastructure and acquisition of those ingredients make this an optional advanced branch rather than first-day storage.

1. Craft Planarium and place with free space above: shape extends to1.81blocks tall and canSurvive requires above block empty.
2. Name it using custom-named item from Anvil or Name glyph. On item placement applyImplicitComponents reads CUSTOM_NAME; `setName` and Name effect resolve hook call setDimension. Native guide explicitly supports both routes. Name glyph's normal personal casting cost belongs to its spell; Planarium naming/creation methods have no additional Source/material debit.
3. A name resolves a persistent **server-wide name-to-dimension mapping**, stored in overworld `an_dimensions`. Reusing exactly the same string reuses its mapping; new string creates random UUID-based `ars_nouveau` key and asks DimensionManager for that level. This is a shared named address, not owner-private space. The inspected mapping has no player UUID/password namespace or per-player ownership check. Effective pack permissions/faction rules remain unverified.
4. Sneak and interact main hand to enter. Without key it sends naming instruction; entry does nothing without existing resolved level. `sendEntityTo` uses JarDimData spawn at block X/Z+0.5, **Y+1**. Default saved spawn is(7,2,7), so initial travel coordinates are(7.5,3,7.5). It does not search for a safe floor/collision-free landing. Keep chosen spawn clear and supported.
5. Build inside. Real blocks live in the pocket level; exterior Planarium renders a sampled structure template rather than relocating or consuming your build into a physical inventory. Another Planarium with the same name addresses the same level. Renaming changes address; no dimension deletion/reclaim follows from these inspected naming methods. Breaking/removing a jar is not documented here as deleting its dimension.
6. Adjust entry point with Dominion Wand: boundary first, desired point second, within same jar-type dimension. DimBoundary callback accepts stored destination only when same dimension and innerBox contains its integer coordinates. It saves that block position; actual subsequent landing adds Y+1. Out-of-bounds reports error but returns SUCCESS from this handler, so wand completion alone isn't proof spawn changed.
7. Attempt to break an outer boundary wall to exit. Registered BreakEvent listener detects DimBoundary outside innerBox, requires player.canInteractWithBlock(pos,4), invokes return handler and cancels the break. No boundary item drops; normal removal is not the required result. FakePlayer is explicitly rejected by return handler.

## Geometry, return identity and persistence

Generator makes outer boundary at X/Z=-1 or32 and Y=0 or32, over X/Z[-1,32], Y[0,32]. Interior physical coordinates differ from helper/render bounds: `innerBox = AABB(0,1,0,31,30,31)` uses upper-exclusive contains; template samples from(0,1,0) size(32,31,32), covering X/Z0..31 and Y1..31. Do not turn one of these constants into a blanket claim of uniformly usable32cube. Use a central safe spawn and test edge positions before teaching boundary builds. Generator places Planarium Projector at(0,-1,0) beneath floor origin; tile class itself has only constructor. It is not an independently audited remote projector crafting/automation feature. No native projector recipe was found in the exact recipe inventory.

Entering with ServerPlayer from a dimension absent in DimMappingData saves that player's current GlobalPos and rotation in destination JarDimData. Entering from another mapped jar dimension **does not overwrite that saved return record**. Thus nested-jar travel should not be taught as a simple last-door stack. Return record is per player UUID and persisted, not tied to a particular physical Planarium block's identity. Boundary exit sends player to saved position/rotation if its level still exists; otherwise invokes fallback. Missing record also invokes fallback: player respawn dimension/position when both resolve, else overworld plus `serverLevel.getSharedSpawnPos()` from the jar-level parameter. No safe landing or bed obstruction resolution appears in this fallback method. Actual exit/recovery and server restart behavior need testing before relying on it as secure transport.

JarDimData saves spawn and enteredFrom map and marks dirty on updates. DimMappingData save emits DimList and isDirty always true. Dynamic level creation delegates to DimensionManager; these native call paths do not establish external dimension-manager persistence/backup compatibility on their own. No Source, item or personal mana per-entry/per-exit debit in the inspected travel bodies. Native dimension type has beds work=true, anchors=false, fixed_time18000, natural=false, no skylight, height384/minY-64; these flags don't prove safe respawn, normal mob generation or compatibility with every spell/other mod.

## Projection update and operational boundaries

Server Planarium checks for any player within strict distance64 every200 world ticks; when none, its tile stops projection updates. Native `planariumUpdateRate` defaults5 ticks (range1..200), checks cached template dirty state, and sends a newer snapshot to nearby clients. Registered jar block-break inside innerBox and block-place events mark cached dimension dirty. Other world changes are not all proven to emit these events: spell transforms, fluids, growth, entity/block-entity-only changes and external edits need specific refresh tests. Do not promise continuously faithful live rendering of every change or every entity.

Template load temporarily forces radius3 square of chunks around origin in the pocket dimension:49tickets with ticking=false, captures world structure including entities while excluding AIR, then releases those loads. This is a snapshot loading mechanism, not proof jar farms continue ticking while no player is inside. Camera's unrelated chunk forcing also must not be conflated with a permanent ticking loader. Templates cache by dimension key; server-stop handling clears manager entries. Runtime performance and storage growth across many names remain unmeasured.

## Walkthrough and acceptance handoff

Optional stage after Apparatus/Stable Scroll: obtain Planarium -> name/place -> enter -> place modest identifiable build -> safely set/test spawn -> exit boundary -> observe exterior projection -> same-name second access. Teach named dimensions and return semantics explicitly. Item possession detects crafted Planarium only; name/entry/exit/render accuracy require manual observation or purpose-built detector. XP plus ordinary building blocks are safe reward directions; avoid creating gated dimension transport or free second advanced device through rewards.

Unrun disposable-world tests:

- Positive: named Anvil item and Name glyph routes, main-hand sneak entry, default and custom spawn, actual exit and retained blocks, second same-name jar versus differently named jar. Record resolved keys and return coordinates/rotation.
- Boundaries: unnamed interaction, blocked/unsupported spawn and innerBox edges; two players same name; nested jars; missing return record/return level; break-and-replace/rename/restart. Verify every player can recover before encouraging extensive builds.
- Projection: ordinary place/break, growth/fluid/spell transform/entity changes; near versus distant players; compare real build and rendered snapshot. Test unloaded/empty dimension without assuming ticking automation.
- Effective pack: claims/access/faction rules, transport restrictions, backup/restore of dynamic dimensions and named mapping. Source findings do not authorize bypasses or claim these integrations work.
