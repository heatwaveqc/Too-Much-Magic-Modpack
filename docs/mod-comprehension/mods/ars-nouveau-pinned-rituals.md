## Load, augment, activate and pause

Craft Ritual Brazier and chosen tablet through named native Notebook/Crafting/Ritual Index and exact recipes below. Tablet useOn a RitualBrazierTile installs a fresh registry ritual, lights brazier and consumes1tablet except infinite-materials player. **canTakeAnotherRitual is `ritual==null OR ritual.isRunning()`** in this exact version: an already-loaded not-started ritual rejects another, while a running ritual can be replaced. setRitual does not call old ritual.onEnd or refund its items in that method. Do not teach replacing a running ritual as a harmless pause/reset.

Before activation, feed accepted augment item directly main hand or as loose ItemEntity within brazier box inflate1. Server scan every5ticks; canConsumeItem is ritual-specific, defaultfalse. Default onItemConsumed splits1unit into consumedItems. Some subclasses override this; table roster distinguishes accepted choices from a claim every ritual accepts every essence. Once running, ordinary tryBurnStack rejects augmentation.

Empty-main-hand interaction calls startRitual(player) if loaded/notdone. The native block routes nonempty held item into augmentation attempt, so stop holding augment/tablet when activating. Start checks ritual.canStart and not already running; onStart records started=true and optional initiating UUID. A Light effect/automation can use other hooks; do not assume every automated start has a Player owner.

Redstone neighbor event records isOff=hasNeighborSignal and calls onStatusChanged; powered can also call startRitual(null) when eligible, but normal tick immediately returns while isOff. Consequently power can prime/start state while pausing work; removing signal resumes ticks. It is not a generic redstone-paid completion. A configured Brazier Relay can redirect ritual ticking/effective position when loaded and correct block entity, while Source check originates from primary brazier helper call. Exact relay acquisition/range and addon behavior remain parent follow-through.

On completion, tick calls onEnd, clears ritual, extinguishes brazier. Player destruction calls onDestroy; only a loaded ritual **not running and not done** refunds tablet and consumed augment item stacks as loose drops. Running/completed operation is not refunded by that branch. Spawn/drop returns are unchecked; final delivery must be observed.

## Source is requested by the ritual, not one universal start fee

Abstract getSourceCost defaults0; consumesSource is cost>0, and context initially needsSource=false. Source-consuming subclass work toggles needsSource or calls takeSourceNow. Brazier tick when payment pending calls `SourceUtil.takeSourceMultipleWithParticles` with range parameter6 and cost; success clears need, failure backs off20 counter ticks and suspends further ritual tick. It can draw multiple nearby containers through that helper, not a required fluid tank. These are Source units, distinct from personal spell mana/XP.

A cost in roster is the amount **per pending request**, not automatically a total ritual price or debit before first effect. Restoration/Containment set need after doing a batch; RangeEffect attemptRefresh applies effect then sets need. First action and subsequent payment order therefore matter. Tests should compare empty/full Source and first/subsequent operations, not assume every nonzero-cost ritual cannot ever act while empty.

RitualContext NBT includes progress, complete, started, needsMana flag and consumed item list. Base ritual also serializes additional identity/context, and subclasses may save trackers/targets differently; do not promise every temporary world/entity reference survives reload just because generic progress does. No live persistence verification.

## Four deep-audited branches

**Wilden Summoning / Chimera gate:** without all three consumed native Wilden Horn/Wing/Spike, chooses random Stalker/Guardian/Hunter at server gameTime%60; progress increments every20ticks and ordinary branch finishes when progress>=15 at summon check. Augment acceptance uses Wilden-drop tag, but boss condition checks each exact native item, not any three tagged drops. With all three it waits progress>=8 at60tick check, creates Chimera above brazier and attempts clearing X/Z±5,Y+1..+5, respecting entity-grief and block hardness/harvest checks used by its helper. This is a destructive encounter; prepare remote arena. No Source override (declared0). Actual boss kill/Tribute acquisition is separate from summoning and advancement feedback.

**Containment:** radius3 block box for jars and capture entities, checks every60ticks server. For empty placed Mob Jars, iterates eligible nearby entities, stops passengers/riding, handles leash and raid membership, then setEntity and discards original only after successful jar assignment. A batch can capture multiple entities into multiple empty jars before setting Source need500 once afterward. Do not charge/promise500 per individual captured mob from this method.

canJar priority: entity type in JAR_WHITELIST immediatelytrue **before** blacklist/type checks; then blacklist rejects, PartEntity rejects, item-capture-blacklisted ItemEntity rejects, remaining default needs alive/nondead LivingEntity excluding Player. Thus a whitelist override can admit special nonliving examples (lightning/clock achievement branches exist), while tag presence/effective pack rules determine actual candidates. No global safe-boss capture claim or ownership/private-pet guarantee. Native Mob Jar contents then feed separate Drygmy/utility systems; eligibility/protected loot remain separate audits.

**Restoration:** every100ticks living entities in box inflate5; Zombie Villager invokes startConverting(optional first nearby PlayerUUID,0) without a Weakness or Golden Apple gate in this body. Other inverted-heal/harm entities take10fake-player-attributed damage, injured ordinary living heal10. If any action occurs, requests Source200 **after batch**, not per target. Full-health ordinary entities do nothing; native cure/discount event and effective undead/protection behavior require acceptance. Distinguish from Occultism Cleansing's Weakness-gated conversions.

**Flight:** range effect declares range60, duration1200 and cost200 per request. Player jump handler attempts grant when no current Flight effect. RangeEffect.shouldApply requires not pending Source and distance helper<=range; apply preserves prior flying state in client update, then requests Source. Normal refresh is handled by native ritual/event queue; this is not global permanent flight or an ordinary potion-anywhere guarantee. Need actual player near ritual/relay plus effect refresh, and effective flight/protection settings may alter practical behavior. Multiple player applications/payment order must be tested, not extrapolated from one receipt.
