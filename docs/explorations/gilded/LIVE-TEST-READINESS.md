## Re-review: Ars enchantment hooks, native Piglin AI, and Gilded golden-food double nutrition (2026-11-16)

**Owner-locked addition:** While already enrolled in Gilded, **all qualified golden/gold-crafted foods** restore **2× normal hunger and 2× normal saturation gained** (ordinary vanilla food-bar/saturation caps still apply). Qualifiers are the explicit gold-food tag, including enchanted golden apples, or a valid gold-containing crafting recipe including nested golden-food ingredients; the *other* Nether foods remain at 1×. No second portion consumed and no duplication of special potion effects or achievements. The ritual item eaten *before* becoming Gilded receives ordinary values; later golden meals receive the perk.

**Food implementation is simpler than previously rated.** The pack already authors Dragon diets through `kubejs/data/dragonsurvival/data_maps/dragonsurvival/dragon_species/diet_entries.json` (native Dragon Survival species-specific override) and `kubejs/server_scripts/dragon_diets.js` (dynamic item tags). These are reusable patterns, **not a directly installable Gilded diet**, because the Gilded player path is not a Dragon Survival species. NeoForge `LivingEntityUseItemEvent.Start` and `Tick` are cancellable, letting a joined-player rule stop disallowed food early; inspect special instant food, bowls, serving blocks and client parity. At successful `Finish`, `ProgressionEvents.consumedFood` already receives the original stack. The proposed minimal player-only bonus is exactly one additional `player.getFoodData().eat(original FoodProperties)` for gold-qualified foods: its base nutrition and saturation are added a second time with normal caps, *without running potion effects a second time*. Alternatively KubeJS 1.21.1 offers `ItemEvents.foodEaten` and `player.addFood`, but the existing Java progression event provides a clearer owner-aware hook and single-award bookkeeping. **Do not change global food components through KubeJS `ItemEvents.modification`.** Critically, food saturation **points** double, but the saturation modifier must **NOT** double along with nutrition: that would quadruple effective saturation before capping.

**Exact pack-pinned Ars Nouveau source**: `baileyholl/Ars-Nouveau@4d323fba9200c3293a4f4848cf1e0fe70beb7098` is `ars_nouveau-1.21.1-5.13.5` per `docs/mod-comprehension/mods/ars-nouveau.md`. Its `LootingPerk.java` registers the Thread of the Drygmy as a carried attribute, and its `common/mixin/looting/EnchantedCountIncreaseFunctionMixin.java` and `LootItemRandomChanceWithEnchantedBonusConditionMixin.java` **wrap the native loot function's existing enchantment-level lookup** and add virtual Looting without adding another loot roll. The Drygmy familiar has a TODO for an older Looting event and supplies a potion effect; **it is not a demonstrated virtual Fortune example**. This is a strong, version-aligned reference pattern for modifying **Fortune** in `ApplyBonusCount.run`, based on actual block `LootContextParams.THIS_ENTITY` and `TOOL`. Use the context to require the actor is a joined Gilded and the actual active tool is gold/Netherite; add virtual +1–3 to actual Fortune exactly once, preserving Silk Touch. Do not inject loot duplication. NeoForge 1.21.1 also has `GetEnchantmentLevelEvent` and `IItemStackExtension#getEnchantmentLevel`; this may be a cleaner shared virtual-enchantment primitive **if** exact actor ownership can be passed or scoped. The raw event supplies **ItemStack, not player**, so a naïve unconditional listener would buff dropped, traded or machine-used gear. Check exact use sites before selecting it; simple item equality alone does not establish valid action context. For Unbreaking, also verify player/equipment context at actual durability wear, not merely the stack's enchant value.

**Piglin/Brute AI is also more tractable.** In Minecraft/NeoForge 1.21.1, the passive sensor checks whether a player lacks gold armor, guarded-block and container alarms invoke `PiglinAi.angerNearbyPiglins(Player,boolean)`, and the Brute logic has `PiglinBruteAi.findNearestValidAttackTarget`. For **alarm causes**, a narrow cancellable Mixin at `angerNearbyPiglins` when the triggering player is joined Gilded prevents anger **before it starts**, without wiping other Piglins' memories. For passive targeting by either ordinary Piglins or Brutes, existing `compat/progression/.../ClassAbilities.targetChange` already handles `faction_neutrality` with a 600-tick (30-second) direct-attack retaliation marker; reuse its `LivingChangeTargetEvent` pathway for Gilded entity selectors, with the same exception semantics. Avoid suppressing group retaliation on a Gilded-initiated attack; inspect broadcast anger pathways in the exact runtime. If target-change filtering is too late for a sensor-memory edge, add a targeted sensor eligibility filter, **not a periodic anger-memory cleaner**.

**Revised engineering risk:** virtual Fortune = **medium** (direct precedent; principal risk ownership context and modded loot interoperability); ordinary Piglin + Brute AI = **low/medium** (known cause and target seams; retaliation/regression tests); Gilded food restriction and golden-food bonus = **low/medium** (existing species-tag pattern + per-player event; hard cases are dynamic recipes/served food); use **medium** for Unbreaking until equipped-item/durability context is source-checked. None of these is implemented by adding this note.

Correct in-use ownership, competing mod handlers and real client/hostile behavior still require tests. Gold-equivalence and Unbreaking remain medium; all eight work packages still must be live before marking ready.
