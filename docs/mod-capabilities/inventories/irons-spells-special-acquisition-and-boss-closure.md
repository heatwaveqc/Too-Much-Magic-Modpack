### Why the apparent source contradiction is not a contradiction

The previous conclusion that these two are **unobtainable player spells** considered `allowLooting() == false` but not the explicit loot filter. [`SpellFilter.getApplicableSpells`](https://github.com/iron431/irons-spells-n-spellbooks/blob/v1.21.1-3.16.3/src/main/java/io/redspace/ironsspellbooks/loot/SpellFilter.java) handles three branches:

1. If a loot JSON supplies an explicit nonempty `spells` list, its entries are filtered **only by `isEnabled()`**, **not** `allowLooting()`.
2. A school-filtered or generic spell roll normally filters out spells whose `allowLooting()` is false.
3. [`RandomizeSpellFunction.run`](https://github.com/iron431/irons-spells-n-spellbooks/blob/v1.21.1-3.16.3/src/main/java/io/redspace/ironsspellbooks/loot/RandomizeSpellFunction.java) invokes **`applicableSpells.getApplicableSpells()`** and writes SpellData to the resulting Scroll. It **does not** apply an additional `allowLooting()` filter after selecting that explicit list. A separate `SpellFilter.getRandomSpell(random)` helper *does* impose a second no-looting check, but **this is not the function used by the JSON `randomize_spell` loot pipeline**.

Therefore: **exactly two active spells are default Forge-disabled; neither enters general random loot; both are deliberately player-accessible through specially targeted loot**. Treat an explicitly configured `isEnabled=false` or TMM datapack deletion as a separate *loaded integration override*, not default source fact. TMM repository code searches for `raise_hell`, `fang_swirl`, the two loot table names, and `loot_table/` did not locate a TMM-authored override in inspected search results, but **search is not a full loaded datapack proof**.
