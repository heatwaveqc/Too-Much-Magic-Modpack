# Malum 1.8.2 — Berserker constructor and native pouch policy review

**Scope:** original exact-version open source review, now supplemented by owner-supplied, fully SHA-512 matched Malum and Gaze published JARs; source compared against [Malum source snapshot `03b743a37f3eeb0cc7f4364f0730e1f135f78408`](https://github.com/SammySemicolon/Malum-Mod/tree/03b743a37f3eeb0cc7f4364f0730e1f135f78408), the version matched in TMM's Packwiz pin. This remains static analysis **plus new exact published-JAR bytecode checks**; no server/client boot or gameplay test. Distinguish observed code paths from real game results.

## Berserker Geas — identity mismatch confirmed in versioned source, runtime severity not proven

The original source and **published Malum 1.8.2 constructor bytecode agree**: [`BerserkerGeas.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/geas/pact/wicked/BerserkerGeas.java) calls **`super(MalumGeasEffectTypes.PACT_OF_THE_REAPER.get())`**. That differs from [`MalumGeasEffectTypes.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/registry/common/magic/MalumGeasEffectTypes.java), which correctly registers `pact_of_the_berserker` with `BerserkerGeas::new` and `pact_of_the_reaper` with `ReaperGeas::new`.

**This is a genuine source identity defect, not proof of a completely nonfunctional Geas.** Traced code:
- [`GeasSoulData.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/data/attachment/soul_data/GeasSoulData.java) persists **registry GeasEffectType entries**, not each instantiated `GeasEffect.type` field. It recreates effects by iterating registered types and calling `geas.createEffect()`, then creates item/display stacks from the **registered type**. Therefore the bad constructor does not by itself prove the saved entry silently changes to Reaper, or that the visible Curios item becomes Reaper.
- [`GeasEffect.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/core/systems/geas/GeasEffect.java) stores its constructor `type` and derives `getModifierId()` from it. Identity-sensitive methods could conflate Berserker with Reaper. But **Berserker does not override `createAttributeModifiers` or call `getModifierId` in its own source**, so no actual modifier collision has yet been demonstrated for this exact combination.
- The Berserker class independently implements damage-build-up/decay, incoming pre-damage ×2, and delayed outgoing Spirit-impact hits at stored-damage thresholds; its behavior is not a delegated call to `ReaperGeas`. In the source, each incoming `LivingIncomingDamageEvent` adds to a `storedDamage` float, `LivingDamageEvent.Pre` doubles incoming damage, `EntityTickEvent.Pre` decays storedDamage every 40 ticks (5%), and qualifying outgoing damage at storedDamage >= 4 schedules repeated delayed damage before reset next tick. This deserves cautious testing, not a declaration that the damage events never fire.

**Focused Type C QA, when authorized in an actual build:** bind Berserker to a disposable player; verify registered `malum:pact_of_the_berserker` persists across logout/relog without Reaper replacing it; test the cost (extra received damage) and benefit (delayed Spirit impacts after accumulating damage); compare only the expected distinct Reaper/scythe effect using a controlled opponent/dummy. Test interaction with any *simultaneously bound* Reaper only if this is legal under native slot limits; inspect modifiers/identity and distinguish external damage modifiers. Record exact client version/logs. Do not patch native code or invent an FTB quest detector based only on the constructor. A separate patch/compat proposal requires an observed impact or explicit owner approval.

## Native Soulwoven/Ravenous Pouches — broad item containers, not Spirit-only

Exact-version sources:
- [`MalumPouchItem.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/item/curiosities/pouch/MalumPouchItem.java) supports secondary-click insertion/extraction and shows generic bundle-style fullness.
- [`MalumPouchContentsComponent.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/data/component/pouch/MalumPouchContentsComponent.java) makes insertion conditional on **`stack.getItem().canFitInsideContainerItems()`**, weighted capacity and available room; no `malum:spirit`-only condition or TMM `#tmm:portable_bags` tag check appears in this route.
- [`SoulwovenPouchItem.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/item/curiosities/pouch/SoulwovenPouchItem.java) enables ground-item auto-collection only for `MalumTags.ItemTags.SOULWOVEN_POUCH_AUTOCOLLECT`; **manual inventory storage remains generic** within `canFitInsideContainerItems()`.
- [`RavenousPouchItem.java`](https://github.com/SammySemicolon/Malum-Mod/blob/03b743a37f3eeb0cc7f4364f0730e1f135f78408/src/main/java/com/sammy/malum/common/item/curiosities/pouch/RavenousPouchItem.java) auto-collects dropped items whose types are already stored, again through generic weighted storage. Dropping contents can preserve a one-item seed of each item type.

**Policy consequence:** neither native pouch is safely described as Spirit storage or an approved magical-only alternative to a general backpack. Owner has not approved them as a new generic storage progression reward; `ML-15` and `ML-16` stay design-held. This is a gameplay availability/reward policy question, **not** evidence that all built-in Malum pouch recipes are already disabled. Respect any explicit future exception and preserve source facts.

**Separate release blocker:** [#16](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/16) requires **all** portable containers to reject other portable containers. `canFitInsideContainerItems()` may reject some mod bags but is **not** the required cross-mod `#tmm:portable_bags` compatibility enforcement; test actual bag pairs and all insertion paths. A content ban and a nesting ban solve different problems. If these pouches remain obtainable, add their exact IDs to the central tag and server-side destination guard; if disabled from new acquisition, also handle preexisting contents safely.

## Gaze Spirit-Channel Pouch — exact pinned JAR confirms generic, remote logistics

Both directly inspected owner JARs match TMM's pinned SHA-512s. `com.strawberry.gaze.common.item.curiosities.SpiritChannelPouchItem extends malum.common.item.curiosities.pouch.SoulwovenPouchItem`, calls its superclass constructor, and uses the same `MalumDataComponents.SOULWOVEN_POUCH_CONTENTS` storage component. `MalumPouchContentsComponent.Mutable.tryInsert` uses `stack.getItem().canFitInsideContainerItems()` and remaining weight—not a Spirit-only filter or TMM portable-bag tag. Pinned Malum `SoulwovenPouchContentsComponent.getStorageSize()` returns **512 weighted units**, inherited by Gaze's variant.

Exact recipe `data/malum/recipe/spirit_infusion/spirit_channel_pouch.json` consumes a normal **Soulwoven Pouch ×1**, **Hallowed Gold Ingot ×6**, **Umbral Spirit ×1** and **Eldritch Spirit ×18**, producing `gaze:spirit_channel_pouch`. It is not an independent Spirit-slot container; it is a general pouch with a new routing mechanism.

The exact `SpiritChannelPouchItem.use` class shows:
- **Shift + use:** store the user's current BlockPos + Dimension key in `DUMP_LOCATION` and `DUMP_DIMENSION` item components.
- **Use with contents:** reject missing target/dimension, reject cross-dimension targets, reject unloaded target chunk; if same dimension and target chunk loaded, create item entities at the saved position and **clear all pouch contents**, then apply a **200-tick use cooldown**.
- It neither teleports the player nor remotely inserts directly into a target container inventory; it **drops item entities** at a saved position. TMM pickup/loot/storage mods could subsequently interact with those entities: separate QA concern.
- Its tooltip computes displayed fullness using `weight ×128` while printing denominator `256`; inherited effective capacity reads `512`. This is a likely display inconsistency, **not** evidence of a lowered storage cap. Verify in client if changed.
- Normal pouch manual insertion, eligible auto-pickup and own secondary-click storage remain inherited. The same release therefore conflicts with **both** TMM's no-generic-backpacks and no-generic-logistics selection unless there is a specific owner exception.

The correct category is **confirmed general backpack with bound-position item ejection**. This settles the technical storage classification; only owner policy disposition and first-party bridge/reward gating remain open. Exact trace: [pinned Gaze census](gaze-1.1.7.1-verified-jar-census.md). #16 nesting rejection must cover it if survival or creative-mode legacy inventories may contain it.
