## Included

1. **One ordinary external blood fluid target:** `evilcraft:blood` on supported ordinary bucket/recipe boundaries; `evilcraft:bucket_blood` from the native Neo Vitae Ara Vitae 1,000-EV bucket ritual, no replacement of EV meter/capability. Source tag extension accepts EvilCraft/Hexerei/Iron ordinary blood as Neo Vitae inputs; native Neo Vitae fluid output/pipe drainage still returns its native fluid until a separately audited capability patch.
2. **Two existing cauldron identities preserved:** Hexerei retains `hexerei:blood_fluid` in its own tank; Iron's can still generate `irons_spellbooks:blood` from damage. Explicit 250 mB vial and 1,000 mB bucket recipes convert only at their boundaries. Native Iron's blood remains extractable to ordinary blood vial despite canonical input recipe changes.
3. **Ordinary bottled reagent compatibility:** `tmm:ordinary_blood_bottles` contains **only** Iron's `blood_vial` and Hexerei's `blood_bottle`, which can substitute in Netherite Spell Book and the three Hexerei broom recipes. The Iron's vial obtains native drink/food usage and one empty glass-bottle remainder from KubeJS startup. No change to native JAWR Wine Glass/Bottle item food components.
4. **Strictly JAWR-native bottle handling:** `witchery:bottle_of_blood` is ONE item with ordinary, chicken-marked, and vampire/Lilith-marked data-component variants. Only stacks with neither `CHICKEN_BLOOD` nor `VAMPIRE_BLOOD` component present are eligible for generic cauldron conversion; component `BLOOD` source UUID alone is not disqualifying. Chicken/vampire markers are protected **even if stored as false**. The native JAWR-only `JAWRVampireProbe` verifies live vampire status, replacing the deleted legacy TeamLapen-era `VampireNativeAccess`. The bridge resolves JAWR registry components after registry setup, resets static resolved state at server stop, refuses canceled cauldron interactions, and requires full 250 mB simulated/real tank acceptance before consuming the bottle. Hexerei's pinned MixingCauldronTile directly implements `IFluidHandler`; when its BLOCK fluid capability is absent, the bridge uses that **native** tile handler rather than bypassing quantities or modifying internal fields.
5. **Drink behavior:** a completed ordinary Iron's or Hexerei blood-bottle use credits native JAWR **+500 blood** to an actual native vampire through `BloodPoolHandler.increaseBlood`. Ordinary native JAWR bottle already handles its own +500, so the bridge gives it *medicine only* and never adds the blood twice. Iron's and ordinary JAWR blood receive Hexerei-style 200-tick Absorption I plus milk-cure effects; Hexerei's existing native medicine is not doubled. Special JAWR bottles retain native consumption and progression. These are source implementations awaiting gameplay validation.

## MXP relationship: important hard boundary

The [MXP/JAWR integration #281](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/pull/281) already provides `MxpService.jawrCommittedBloodDebit(player, tx, originalCost, actualDebit)` using a planned **900-blood first-access reference** with growth factor **1.02**. This API is a **payment** reward hook, not a resource-refill reward. **This bottle bridge must not call that API.** Ordinary blood collection, vial/cauldron transfer, healing, drinking, crediting JAWR +500, and vampire transformation are **NOT MXP-eligible actions** by themselves. A *future separate source-verified actual native blood debit* integration should invoke the payment API **once, after a committed supernatural action**, with shared transaction IDs to deduplicate Ars/Iron/other co-payments. The missing native payment hook remains open in [issue #280](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/280).
