# Reviewed integration batches (TMM)

Owner-approved 2026-11-24. This local procedure supplements the existing designated-writer, source-readiness, branch-lifecycle and quick-CI contracts. It does not alter repository protection or authorize game boot, assembly, release, packaging, deletion or bypass. Native GitHub merge queues are unavailable for the current personal-account repository. Use one protected integration PR for a verified group rather than repeatedly rebasing independent PRs after every individual merge.

## Batch admission and transaction

1. The designated integration writer selects a small group of independently coherent, owner-approved PRs with `status: ready-for-integration`, exact green applicable source CI, identified issue/QA handoff and target. Record every PR, exact source head, original base, unique paths, dependencies, checks and designated writer. Never combine unreviewed code, owner decisions, unresolved failures, or unrelated subsystem targets simply to increase throughput. Separate high-risk runtime and shared-manifest changes from independent research/docs where practical. Check prior integration/duplicate work.
2. Freeze the current target SHA. Reconcile each candidate's actual change against that tree, including old and new rename paths, removals, modes and exact blob identities. Disjoint paths may be batched; overlapping paths require explicit three-way reconciliation, applicable subsystem review and fresh evidence, or hold the PR. Do not restore old directories, overwrite newer changes, or copy entire old trees. For Packwiz/config changes reconcile index and pack hashes, manifests, ownership and exact external sources. For stacked work, preserve prerequisite ancestry and retarget dependent PRs before any meaningful merge could delete their base; otherwise hold. Check frozen donor references before merging.
3. Use an isolated temporary integration batch branch and one reviewable PR with a batch manifest/crosswalk in its description; use merge commits with original source heads as ancestors where feasible. Construct the combined tree from the frozen target plus approved changes; verify complete tree diff is exactly the intended paths and exact selected blobs, with no additional files restored. Keep source PRs and refs intact until batch validation and merge. Explicitly designate the batch PR as their single integration successor, not parallel coding work. If baseline moves, revalidate and synchronize non-destructively; if a source head moves, exclude or re-review.
4. Require Repository CI, Integration Preflight and every applicable Module CI on the exact combined candidate; do not substitute historical source checks for combined checks. Confirm workflow triggers, no full build jobs, actual current target and all source heads before the SHA-guarded normal PR merge. Do not weaken branch protection, directly push to shared targets, forge statuses or use skip-ci. If any check fails, investigate or split the batch; no partial success claim.
5. After merge verify live target ancestry and intended path/blob preservation; record actual batch and source merge/ancestry SHAs. Verify each donor PR's real GitHub merged state; if a donor remains open, close as superseded only with preservation evidence and successor link, not a fictitious merge. Preserve active dependent refs and immutable donors; ordinary auto-deletion allowed only if safe, other retirement remains separate owner-approved process. Reconcile issue status, canonical ledger and runtime QA obligations per slice; docs/research can complete at accepted evidence, integrated runtime work awaits authorized build. Report actual PR merges separately from source PRs integrated through the batch and closed-unmerged. No full assembly, boot, Prism package, gameplay or release is implied.

This is a manual, repeatable integration-batch procedure, not an unattended queue service. A single writer serializes final batch merges; prepare compatible work in the same batch rather than repeatedly advancing the target for isolated changes. Automated or scheduled mutation requires separate reviewed implementation and local authority.
