## Concrete blockers to copying old code as-is

1. **Old ID/API pointer:** `NativeSpeciesJoinGuard` checks `ModList.get().isLoaded("tmm_progression")` and reflectively loads `io.github.heatwaveqc.tmm.progression.core.ProgressionApi`. Current Progression is **`tyr_progression`**, Java package **`io.github.heatwaveqc.tyr.progression`**; so the old cross-module join bridge is stale. This is source evidence; **not** a claim the game was newly booted/tested.
2. **Wrong Path join semantics:** `SpeciesEnrollmentPolicy.canAcquire` blocks new native forms after *any* joined Progression Path, while `canJoinHumanPath` blocks joining a Progression Path with *any* native physiology. Current owner target has **Newbie and Normie baseline Paths** and explicitly allows **Dryad + Forest Dragon, Sexy Demon + Cave Dragon, Spawn + Sea Dragon** (#452). The old blanket human-only policy **must be replaced with data-driven compatibility** rather than copied.
3. **Potential stale ritual/classifier assumptions:** `TransitionPolicy.assess(..., ABOMINATION_RITUAL)` currently models an Archlich + both lich states as a prerequisite for Abomination; owner target describes **Vampire + Werewolf**, not an Archlich hybrid. Do not carry retired classifications or old mutual exclusion forward without reconciling with native/provider state.
4. **Optional adapter safety is not just a mod-loaded check:** `tmm_transformations.mixins.json` is **required: true**, with multiple `@Pseudo` mixins and `injectors.defaultRequire=1`. Current `DracolichMixinPlugin` pre-gates mixin classes whose names begin `Dracolich` using exact versions; **other optional target mixins** are not covered by that plugin condition. Any merge needs mixin plugin gating per source mod/version, deferred class references, correct client/server separation and startup checks when optional dependencies are absent/mismatched.
5. **Runtime registration/order:** Current `TransformationsMod` immediately registers adapters, network handlers, attachments, Archlich/Dracolich death events, Mob Alliance and JAWR bottle use. Avoid registering both old and new handlers (duplicate death interception, duplicate bottle gain, listener ordering). Preserve one authoritative registration per feature and prove atomic handoff.
6. **Active config/resource/registration cleanup (no old saves):** The old `tmm_transformations:review` attachment, `tmm_transformations:` entity tags/assets, `/tmmtransform` command, archlich config and network payloads are references to reconcile in the new single-JAR build. **No backward-compatibility, save migration, old command alias or old config preservation is required** because there are no established worlds. Remove dead review-only state if unneeded, choose fresh Progression namespace, update all active references, and retain complete effective functionality/assets.
7. **Existing Progression already has optional diet hooks** (`tyr_progression_diet.mixins.json`) and join-veto API. Reuse these rather than introduce a second new diet-per-path runtime. The new owner-approved dietary evaluator should be in `compat/progression` with **strict allow**, **nutritional affinity**, **native penalty exemption**, **one-time bonus**, **custom resource feeding**, **stack-provenance override** and explicit native consume semantics.

## Owner-approved new tag names and dietary-policy ownership

- Use owner-specified **`#c:food/bloody`** (blood-containing consumables; not automatically permission, not inherently a fixed JAWR blood reward), and **`#c:food/recreational`** (intentional recreational food-backed drinks; exclude mandatory magic/medicinal potions and ordinary nourishment unless explicitly classified). Both are new shared *item* tag names. **Note**: the owner used singular `food/` while existing other common tags use plural `foods/`. Preserve owner's spelling in this source-only record rather than silently renaming; confirm naming prior to executable schema.
- `tyr_progression` owns a **single reusable dietary-policy evaluator**; source mods retain native feeding mechanics, status effects, provider attachments and original consumable behavior unless a specifically approved adapter changes them.
- The recipe classifier generates independent shared item tags (`#c:foods/nether_only`, `#c:foods/with_nether`, `#c:foods/raw_nether`, `#c:foods/golden`, `#c:foods/raw_fish`, `#tmm:foods/magical`) and Path policies consume them. Do not globally modify vanilla food components or mistake Dragon nutritional affinity for Gilded/Dryad's hard restrictions.
- `#c:food/recreational` is a **classification**, not an unrestricted food/drink permit: Gilded/Werewolf baseline alcohol and Acquired Taste rules and vampire native penalty remain; spell potions and medicinal drinks must still work. `#c:food/bloody` identifies blood-bearing things, while specifically approved blood meals/wine use a separate, precise native JAWR amount/effects handler.

## Suggested non-destructive migration

1. **Policy layer first** in Progression: pure native-provider observations, effective physiology arbitration, Newbie/Normie semantics, Path-species compatibility from config, unified dietary evaluator, unit tests. Keep existing Transformations JAR unmodified during parallel dry-run, with shadow diagnostics only.
2. **Read-only probes + join-veto replacement:** register one central native species guard, update mod IDs and API package, test all approved pairings, forbidden combinations, initial join/graduate/cure/relog/death, and ensure no double gates.
3. **Optional source-mod adapters:** move JAWR blood meals, alliance hooks and lich/dragon arbitration behind exact dependency/version checks; register exactly one native handler. Native forms/feeding always remain source-owned.
4. **Visual pipeline last:** port client-side Dracolich assets/mixin/networking and compare identical model behavior under authorized client QA. The **authored visual content must survive**; retaining the old resource namespace or identifiers is **not** required if all references migrate coherently and tests pass.
5. **Delete/retire old JAR after source parity:** update new-engine config/data/commands without legacy aliases or attachment migrations, ensure one listener and one mixin owner per feature, reconcile packaged artifacts/index/root hash. In-game B/C tests and existing integration/QA authorization remain required.

**Approved end state:** One physical Progression JAR with **conditionally registered, version-pinned adapter packages**, NOT dynamic hot-loaded sub-JARs. Core works when optional mods are absent. Keep Dracolich renderer and unrelated Botania/Mahou hooks internally isolated for source ownership and QA, **not** physically in a separately deployed Transformations mod. Owner confirmed no legacy worlds; retire standalone Transformations after parity and integrated QA. See [#468](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/468).
