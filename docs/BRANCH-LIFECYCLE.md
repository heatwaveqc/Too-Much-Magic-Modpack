# Branch lifecycle and integration authority

Owner-approved 2026-11-19. Applies repository-wide; read with [AGENTS.md](../AGENTS.md) and [branch/progression workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BRANCH-AND-PROGRESSION-WORKFLOW.md). Where older instructions require repeated owner approval for ordinary merges within approved scope, this document delegates that review to the designated integration writer. Existing safety/build restrictions remain in force.

## Before writing

- Look up related issues, PRs, branches, source locks and integrated code. Resume the existing workstream, even after a conversation fails; do not fork its work again. Explicitly transfer writing responsibility before resuming another agent's branch.
- Use issues for ideas and postponed work. A branch is for a concrete, reviewable change. **One live feature/workstream PR is the default**, not one PR per owner request, chat turn, agent run, survey or coding increment. Extend an existing owned PR with commits and update its checklist/handoff when subsequent tasks share the same source, target, owner and review boundary. Never create scratch branches for progress checkpoints.
- Before opening a distinct PR, document the specific independently mergeable owner/path/target boundary, material isolation/revert reason, or unavoidable dependency stack. Inspect all open/merged PRs, active branch heads/bases and baseline source first. Keep stacks as short as practical and do not manufacture PRs solely to satisfy the 24-hour clock. Preserve the designated single writer; hand off rather than write concurrently to another owner's branch.
- Every **justifiably created** temporary branch must have an accountable draft/ready PR within 24 hours (prefer immediately after first commit). Handoff: linked issue or workstream ID, designated writer, target, owned paths, approved scope, **why the existing PR cannot be reused**, dependencies/stack, current checkpoint SHA, quick checks, blockers, next step. Maintain that PR across interruptions.

## Continuous integration

Development writers implement and run scoped quick checks; designated subsystem writers reconcile subsystem slices; the modpack integration writer owns shared integration manifests, relocking, collision resolution, readiness and releases. No concurrent writers on a shared branch. The integration writer may merge reviewed, independently coherent slices of already approved work, including routine metadata, policy, configs and bug fixes within approved scope, without another feature approval. Read exact current head/base and check all applicable required quick checks; reconcile shared paths and dependency ordering; use expected head SHA on merge. Do not mark a draft ready merely to bypass a real blocker. Get owner direction for new mechanics, balance, architecture, unresolved design choices or scope expansion. Respect declared workstream ownership and coordinate handoffs. No automatic merge based solely on green checks.

SOURCE READY means ready for integration review, not installed/assembled/server/client/gameplay accepted. Record required future QA and preserve inclusion obligations before merge. A source-ready PR does not require a Minecraft boot to merge. Full assembly, full smoke, Prism package and stable release remain separately owner-authorized. Reconcile manifest donors to baseline-owned or retained immutable, reachable source plus provenance; do not strand active source refs or stacked PRs. Retarget or migrate dependents before a merge that deletes their base. **Donor PR disposition is part of the integration transaction, not optional housekeeping:** reconcile exact source/behavior, record immutable reachable successor commits and linked issue/QA obligations, and inspect open stacked dependents. For each source PR whose unique approved work is completely integrated, add a successor explanation and **close it as superseded without merging its stale head**. For remaining unique work, keep an explicitly owned residual PR with a named next action/review date or migrate the residual slice to the active workstream before closure. A donor's open PR must never be kept solely as the future QA checklist; use the issue/QA ledger. If immediate closure is unsafe, put the precise blocker/owner/next review in a closure queue; do not repeat an unexplained "candidate" across audits. Branch deletion remains a separate restricted act.

## Finish the lifecycle

A task is administratively complete only when integrated or explicitly deferred/closed, handoff/provenance is complete, and the temporary branch is retired or its retention reason and next review date are recorded. Keep existing branch when active. Archive approved historical commits using reachable history or immutable tags only where needed; verify preservation and do not treat an unreferenced SHA as durable archival storage. No dummy merges, force rewrites or blanket deletes.

Permanent allowlist: main, test/full-integration, dev/progression, dev/art. Owner approval required for any additions. Existing other branches are transitional and must be reviewed, not automatically deleted. Protect permanent refs against deletion and force pushes in GitHub settings. Enable native automatically delete head branches for normal meaningful merges, after checking stacked/manifest dependencies.

## Continuous PR lifecycle and reporting

- **Per workstream, maintain one live source PR by default.** Follow-up work goes into the same PR/branch when it is the same coherent review boundary. A justified independent PR records the exception and ancestry; existing legitimate source/Path/config and shared-branch ownership boundaries still apply. When a stack advances, reviewers must consider consolidation or coherent promotion rather than treating all leaves as permanently live features.
- **Each completed integration has an explicit donor disposition:** (1) recorded successor/merged code and preserved reachable source; (2) required source CI/review; (3) exact unique-slice/dependency crosswalk; (4) retained B/C QA in issue/QA register; (5) superseded donor PR closed with explanation, or a documented reason/owner/next review to keep it open. Close the PR metadata only after verifying preservation, but do not require Minecraft gameplay PASS when source review is complete. A separate unmerged closure is not a destructive branch retirement.
- **Every Gravekeeper review includes a closure action, not only an inventory.** Distinguish (a) implementation PRs with unique code, (b) genuine stacked dependencies, (c) integrated source awaiting B/C, (d) superseded donors pending safe closure, and (e) owner/design holds. Present unique unresolved workstreams and open/merged/closed-unmerged/net PR counts. Record real closure decisions and reasons for retained PRs; never imply that a rising open count means no coding progress.
- The integration owner may close safely superseded donor PRs under prior ordinary-integration delegation. **No policy here authorizes silent branch deletion, force pushes, fake merges, new mechanics decisions, a full build, or source release.** Require the separate, exact-SHA owner-approved retirement run for obsolete remote branches.

## Budget and service targets

Normal goal 12–20 total remotes (including permanent); <=20 healthy, 21–30 review, >30 maintenance. Review temporary branch without PR after 24h, ready PR waiting 24h, inactive development after 72h, merged branch surviving 24h, unresolved external donor after 7d. These are review triggers, not hard caps, deletion permission or exact age claims from commit dates alone. Record explicit exceptions with owner, reason and next review. Prioritize ready work continuously; do not wait for release week.

Daily read-only inventory reports branch tips, current open PR heads/bases, frozen external donors, dependency stacks, draft/ready status and age proxies. PR collision report flags exact changed-path intersections among live same-base PRs. Cross-base ownership still needs manual review. Inspect current integration-source manifest and existing Integration Preflight on every relevant PR; read-only inventory is advisory and cannot prove behavior equivalence. Missing/ambiguous data blocks retirement, not a reason to guess.

## Safe retirement

Follow the independently reviewed batch procedure in AGENTS.md. The historical 46-entry runner and manifest are immutable history. For future batches use `scripts/branch_lifecycle.py` and the Branch retirement workflow. Prepare `maintenance/branch-retirement/<batch>.json` in its own main PR, with schema 1, batch name matching file stem, and nonempty branches array of name, full SHA, reason and evidence (issue/PR/commit links). Optional boolean `archive_history: true` requests exact original commit preservation; require it when no durable PR/descendant history is available or a historical build/source checkpoint specifically needs archival. Preserve necessary code and immutable references first. Require dry run against live refs and independent review of all candidates. Keep protected, active or uncertain branches excluded. Merging a reviewed manifest alone never deletes anything. Manually dispatch on main, or use the dedicated owner-authorized console below, with the exact manifest path and SHA-256 of the reviewed bytes; execution requires explicit owner opt-in. Retire only the reviewed batch. For each candidate refresh refs/dependencies, require named ref still at approved SHA, and use Git lease-guarded deletion (no force rewriting). A candidate marked `archive_history: true` receives a create-only lightweight `refs/tags/archive/retired/<40-hex-tip>` tag on its exact approved SHA and a remote verification before deletion. A wrong target or failed preservation stops execution; recheck live dependencies after the tag is verified. This tag is never a release or a deployment marker, and must never be moved or removed. Dry runs never create archive tags. Tag preservation and branch deletion are separate transactions; do not edit archive refs during maintenance. No scheduled/unattended pruning; no automatic retries. Report per-ref results and verify remaining refs. Note: the cross-API PR/manifest snapshot and Git ref deletion cannot be a single atomic transaction; coordinate a maintenance window and do not open new work on nominated refs during execution. Lease guards the ref itself.

## Owner-authorized retirement command console

[Issue #359](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/359) is dedicated to branch retirement only. On an already reviewed and merged batch, submit one new standalone comment:

- `/tmm retire-check <manifest-path> <64-lowercase-hex-digest>` — read-only dry run; no receipt or deletion.
- `/tmm retire <manifest-path> <64-lowercase-hex-digest> <32-lowercase-hex-nonce>` — execute **only after explicit owner consent for this exact batch and digest in the current conversation**, or an explicit owner comment. New approval for each run; policy approval, a merged manifest, or permission to run checks is insufficient.

The comment event invokes the existing retirement workflow directly (not a bot workflow dispatch). It checks exact repository/issue/default branch, owner account ID, fresh unchanged live comment and creation event, exact main SHA and committed manifest bytes, and first run attempt. The execution job alone receives contents write. It atomically creates `refs/tags/retirement-request/<nonce>` pointing at the authorized main commit before invoking the unchanged live-ref/PR/donor/lease checks. The receipt is provenance and replay protection, **not** evidence of deletion. Never delete receipts, replay uncertain commands, or retry a failed run without a fresh owner decision and nonce. The console trusts GitHub owner identity, not a separately authenticated ChatGPT conversation; agents must enforce explicit prior consent. Manual owner dispatch remains available. Read the execution log and recheck remote branches and preserved source refs. No full build authority is granted.

GitHub settings/rulesets are administrative actions outside current connector write access; verify actual settings rather than assuming text implements protection. No workflow in this policy assembles a modpack, boots Minecraft, publishes or builds Prism.
