# TMM branch lifecycle and integration authority

Owner-approved 2026-11-19; shared standards migration #633. This document governs **TMM-specific** authority, ownership, integration, branch budgets and retirement. Before mutations read the canonical [AGENTS.md](../AGENTS.md), its pinned Tyr Development Standards core and applicable `workflows/branch-lifecycle.md`, `workflows/work-management.md` and `workflows/qa.md` routes, and [branch/progression workflow](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/blob/test/full-integration/docs/BRANCH-AND-PROGRESSION-WORKFLOW.md). General lifecycle rules are maintained upstream; this document does not duplicate them. If the shared revision is inaccessible, stop affected mutations.

## TMM-specific integration authority

- Development writers implement scoped approved work; designated subsystem writers reconcile subsystem slices; the modpack integration writer owns integration manifests, source relocking, collision resolution, readiness and releases. Follow the shared one-workstream/one-writer/one-live-PR rules. A distinct PR must explain its actual target, ownership or review boundary and dependencies. Do not mark a draft ready to bypass a real blocker.
- The designated integration writer may merge independently coherent reviewed slices within already owner-approved scope (including policy, metadata, configs and bug fixes) without another routine approval. Use exact current head/base, expected-head SHA, applicable quick checks and reconciled paths/dependencies. New mechanics, balance, architecture or scope require owner direction. Green checks alone do not authorize merge.
- Source-ready does not mean assembled, installed, booted or accepted. Record required B/C QA in the issue/QA ledger, preserve next-test inclusion obligations, and reconcile donors to reachable immutable source or baseline ownership plus provenance. Full assembly, full smoke, Prism packaging and stable release remain separately authorized.
- Each integration records exact unique-slice/behavior and dependency crosswalk, successor and retained QA obligations. Close fully superseded donor PRs without merging stale heads once preservation is verified; otherwise record residual owner, action and next review. Do not retain PRs solely for future gameplay QA. Preserve active stacked bases and frozen source refs before ordinary merge cleanup.
- Gravekeeper reviews distinguish unique source work, stacked dependencies, integrated-awaiting-B/C, superseded donor cleanup and owner/design holds. Maintain a concrete closure-action queue with successor, writer and next review; report actual PR opened/merged/closed-unmerged/net counts and distinct workstreams. Inventory without action or a recorded blocker is not a completed disposition.

## TMM branch limits and reporting

Permanent allowlist: `main`, `test/full-integration`, `dev/progression`, `dev/art`. Owner approval is required for additions. Protect permanent refs from deletion/force pushes in actual GitHub settings; verify settings rather than assume. Native deletion after a normal meaningful merge is allowed only when stacked and manifest dependencies are safe. Other refs are not implicitly authorized for deletion. Target 12–20 total remotes; <=20 healthy, 21–30 review, >30 maintenance. Shared age thresholds are review signals, not deletion permission. Retain explicit exceptions with owner, reason and next review.

The [Branch lifecycle report](../.github/workflows/branch-lifecycle-report.yml) invokes the immutable shared read-only workflow. Scheduled/manual main inventory reports open PRs, refs and age proxies; PR reports check exact same-base changed-path collisions; workflow/policy maintenance PRs also validate inventory. The local donor adapter reads the live integration-source manifest and reports missing refs, missing full SHAs and aged checkpoints (inventory), and passes protected donors to the shared audit. Cross-base ownership needs manual review. Inspect the live manifest and Integration Preflight for applicable PRs; reports are advisory, not proof of equivalence or permission to retire. Missing or ambiguous data blocks retirement. Generic inventory/collision CLI implementations are superseded; use the Actions reports. The TMM retirement console and script remain local.

## Safe retirement

Follow the independently reviewed batch procedure in AGENTS.md. The historical 46-entry runner and manifest are immutable history. For future batches use `scripts/branch_lifecycle.py` and the Branch retirement workflow. Prepare `maintenance/branch-retirement/<batch>.json` in its own main PR, with schema 1, batch name matching file stem, and nonempty branches array of name, full SHA, reason and evidence (issue/PR/commit links). Optional boolean `archive_history: true` requests exact original commit preservation; require it when no durable PR/descendant history is available or a historical build/source checkpoint specifically needs archival. Preserve necessary code and immutable references first. Require dry run against live refs and independent review of all candidates. Keep protected, active or uncertain branches excluded. Merging a reviewed manifest alone never deletes anything. Manually dispatch on main, or use the dedicated owner-authorized console below, with the exact manifest path and SHA-256 of the reviewed bytes; execution requires explicit owner opt-in. Retire only the reviewed batch. For each candidate refresh refs/dependencies, require named ref still at approved SHA, and use Git lease-guarded deletion (no force rewriting). A candidate marked `archive_history: true` receives a create-only lightweight `refs/tags/archive/retired/<40-hex-tip>` tag on its exact approved SHA and a remote verification before deletion. A wrong target or failed preservation stops execution; recheck live dependencies after the tag is verified. This tag is never a release or a deployment marker, and must never be moved or removed. Dry runs never create archive tags. Tag preservation and branch deletion are separate transactions; do not edit archive refs during maintenance. No scheduled/unattended pruning; no automatic retries. Report per-ref results and verify remaining refs. Note: the cross-API PR/manifest snapshot and Git ref deletion cannot be a single atomic transaction; coordinate a maintenance window and do not open new work on nominated refs during execution. Lease guards the ref itself.

## Owner-authorized retirement command console

[Issue #359](https://github.com/heatwaveqc/Too-Much-Magic-Modpack/issues/359) is dedicated to branch retirement only. On an already reviewed and merged batch, submit one new standalone comment:

- `/tmm retire-check <manifest-path> <64-lowercase-hex-digest>` — read-only dry run; no receipt or deletion.
- `/tmm retire <manifest-path> <64-lowercase-hex-digest> <32-lowercase-hex-nonce>` — execute **only after explicit owner consent for this exact batch and digest in the current conversation**, or an explicit owner comment. New approval for each run; policy approval, a merged manifest, or permission to run checks is insufficient.

The comment event invokes the existing retirement workflow directly (not a bot workflow dispatch). It checks exact repository/issue/default branch, owner account ID, fresh unchanged live comment and creation event, exact main SHA and committed manifest bytes, and first run attempt. The execution job alone receives contents write. It atomically creates `refs/tags/retirement-request/<nonce>` pointing at the authorized main commit before invoking the unchanged live-ref/PR/donor/lease checks. The receipt is provenance and replay protection, **not** evidence of deletion. Never delete receipts, replay uncertain commands, or retry a failed run without a fresh owner decision and nonce. The console trusts GitHub owner identity, not a separately authenticated ChatGPT conversation; agents must enforce explicit prior consent. Manual owner dispatch remains available. Read the execution log and recheck remote branches and preserved source refs. No full build authority is granted.

GitHub settings/rulesets are administrative actions outside current connector write access; verify actual settings rather than assuming text implements protection. No workflow in this policy assembles a modpack, boots Minecraft, publishes or builds Prism.
