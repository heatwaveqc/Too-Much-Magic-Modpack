# Production pipeline v0.1
## 0. Freeze the source roster
Use current approved integration SHA and exact packwiz metadata; obtain authorized local copies of Minecraft client assets and official mod releases using existing provider/Packwiz mechanism, verify their lock hashes, and record archive identity/SHA-256. Never commit binaries from upstream. Include content-bearing dependencies and optional approved dimensions; distinguish installed versus planned. Do not assume the bootstrap list is current. Make a temporary scratch directory outside the repo and inventory all namespace/path keys, including nested archives and overlays with separate inspection. Record no-texture libraries only after inspection. Diff successive roster versions, don’t erase existing approved art or invent coverage for missing archives.

## 1. Inventory and plan
Run tools/inventory.py with explicit --source entries for verified local archives (including the vanilla 1.21.1 client JAR). It emits a deterministic partial inventory with path, dimensions, source hash and archive hash. It does not edit the production pack or mark anything approved. Review duplicates, animation metadata, atlas classes, image types beyond PNG, custom model/renderer references, missing archives and generated data. Add every remaining required asset manually with provenance or refine tooling. Merge with registry preserving decisions if original hash/renderer contract unchanged; changes require review. Coverage denominator is exact inventoried assets plus unresolved exceptions, never number of mods or advertised texture count. Track missing archive scope separately and state that global coverage is unknown until complete.

## 2. Pilot
Owner-approved Soartex inspiration, not copied Soartex pixels. Use official upstream preview URLs to study design and actual unmodified native source only to understand semantics/layout. Draft original palette/style sheet, representative vanilla materials and Botania magical family. Establish 64px block and item style, alpha edge treatment, metal/wood/stone/gem hierarchy, magical colors, UV/GUI discipline. Review native scale and in-game across lighting. Record owner approval with style version and exact approved reference filenames/hashes. No claim that the draft palette is approved or gameplay-ready.

## 3. Batch
After pilot approval, choose 10–30 related texture paths initially; choose connected sets/families (all faces, variants, equipment layers), not random across mods. In registry record batch ID, exact source lock, planned ownership, path set, class-specific sizing, status and dependency. Use one branch per batch from current dev/art. Reconcile duplicate assignments and asset names before generation. Shared materials are designed once and reused as original source swatches, but every variant checked independently.
Generate artwork using approved individual/icon/contact-sheet prompt or native procedural paint workflow. Specify subject and mythology, material, silhouette, orientation, alpha, 64px finish, top-left light for icons, material not cast shadow for tiles. Use generous source canvas if needed, crop/align/antialias/downsample deliberately; inspect the native 64 result. Don't use third-party texture PNGs as image-to-image seeds or imitate the exact distinctive drawing. Preserve UV maps from technical layout, not ripped source art. Avoid hallucinated text, symbols that alter mechanics and incidental backgrounds. Use tile-aware periodic procedures or test and repair seams. If image generation cannot conform to UVs/metadata, switch to deterministic painting/vector/raster tools or mark blocked.
Keep raw drafts and reference ZIPs outside Git, save approved output only. Record generation method/tool, prompts or design notes, style version, output hash, review evidence and licenses. A human/agent review evaluates native readability, value structure, silhouette, semantic identity, family cohesion, seam continuity, alpha, animation/UV layout, no copied art and renderer compatibility; rejected candidates stay local.

## 4. Validate and commit
Write production assets at exact paths; merge row updates by key, not whole stale registry snapshot. Run tools/validate.py against updated inventory and asset tree; inspect errors and unknowns, verify source hashes and output dimensions. Structural validator is only initial guard; visual review and game testing are separate. Run isolated script tests; report what was actually executed. Before committing confirm scope via diff, no downloaded art/cache/JAR/ZIP/secret, no gameplay path. PR should summarize added/changed asset keys, style version, exact source SHA, checks/passes/blockers, visual review evidence. Single art writer resolves overlapping claims and merges reviewed batches into dev/art. If binary upload unavailable, report blocker, do not write PNG bytes as text or claim artwork exists.

## 5. Standalone packaging and acceptance
Owner approval required to make/release ZIP; no automatic publication. Pack metadata + assets only at ZIP root, no nested extra folder, registry/references/scripts/caches/rejected images excluded. Validate full path uniqueness/hash and deterministic sorted ZIP build before release; verify actual resource reload (F3+T), logs, textures across vanilla, magic systems, dimensions, gear, entities and UI. Compare FPS/VRAM/launch times with base pack and texture-only candidate. Test with Embeddium/Fusion, darkness, tint/animation/connectivity, no shader dependency. Record test environment, exact SHA, coverage/exceptions, screenshots and limitations. Released asset ZIPs are immutable versioned GitHub Release artifacts; point Packwiz at exact URL/hash only after separate integration approval. No Cathobb dependency in final stand-alone pack. Do not mark incomplete art pack as default or complete without owner decision.

## 6. Recoverability
Each Work session starts by reading this guide, registry and active batch issues/PRs; reconcile predecessor commits before claiming new work. Finish a bounded, coherent batch; do not promise unattended future iterations unless explicit automation exists. Handoff: branch, exact commit, affected paths, counts, checks, blockers, next batch. Reuse the registry; never restart production from scratch.
